# V1.1 数据迁移与现有内容导入

日期：2026-10-26。适用 P6-B 隔离开发环境；本轮没有在生产服务器创建数据库、执行迁移或改变 V1.0 静态内容。

## Schema 1 → 2

`backend/migrations/001_initial.sql` 保持 P6-A 已冻结字节。新增的 `002_content_history.sql` 建立：

- `content_imports`：一次性导入来源完整 Git SHA、逐文件清单哈希、规范化 payload 哈希、导入时间及数量；禁止普通更新和删除。
- `workspace_changes`：每个成功 revision 的管理员、动作、时间及经过校验的修改内容 JSON；禁止普通更新和删除。内容历史属于私有数据库资料，不能输出到公开站。
- 空结构行 `workspace(id=1, revision=0, updated_at=0)`；既有 workspace 使用 `ON CONFLICT DO NOTHING`，不覆盖原 revision 或内容。不生成账户或示例项目。

显式 `homepage-api migrate` 按顺序升级。服务启动和 readiness 只检查，不自动迁移。runner 逐项验证已应用的全部 checksum、连续版本及当前支持上限；旧 001 checksum 变化、版本缺口、未知/更高版本、没有可信迁移记录的既有库均拒绝。升级的 SQL 与迁移记录在同一事务中提交；不提供自动降级或破坏性 down migration。

升级后 P6-A 的 schema-1 程序会拒绝 schema-2 数据库，这是预期的兼容边界。不能仅回退 API 镜像就声称数据库已回滚；需要先确认旧代码兼容，或按独立授权恢复升级前的一致备份。

## 从已确认 V1.0 配置导出

导出器是明确执行的本地开发工具，读取固定白名单中的可信 TS 源文件、Nuxt 元信息、页脚及五份自有静态素材。它不接受任意模块，不联网，不扫描或推断个人经历。项目 API 只接收 JSON，不执行 TS/JS 或调用 Git。

在仓库根目录执行（Node 24、项目依赖已安装）：

```powershell
node scripts/export-admin-seed.mjs e6205c074191a2a1ea021234cf7ae26cc70fbd7a
```

结果固定写入 `backend/seed/v1.json`。导出器将每份来源当前字节与 `git show <完整SHA>:<路径>` 逐一比对；来源改变但仍指定旧 SHA 时直接失败。脚本不以工作区新文档或后台代码冒充原前台来源。

本轮实际导出三项目、三分类、五个 builtin 资源，来源为上述完整 SHA，12 项来源清单 SHA-256 为：

```text
16b09f83320a4e19eb768dc05c773aa49480a019d982e70b79f155e0367dc45a
```

Blog/Nav/ERP 的稳定 ID、slug、分类、顺序、精选、简介、独立占位封面、空技术栈、`unconfirmed` 和空外链保持原值。个人履历和简历继续为空，不从 Git 邮箱推断联系方式。自有 SVG 仅通过固定 builtin 注册表导入，上传接口继续禁止 SVG。

## JSON 与完整性规则

封套字段为：

```text
schemaVersion = 1
sourceRevision = 40位小写Git SHA
manifest = [{path, sha256, byteSize}, ...]
manifestSha256
payloadSha256
payload = {categories, projects, profile, settings, assets}
```

清单记录每份来源的路径、字节数及 SHA-256。payload 包含类型化内容与受控素材 ID/事实，不含密码、会话、CSRF、物理路径或上传原件。哈希输入使用递归按键排序、紧凑 UTF-8 JSON，不进行 HTML 转义，U+2028/U+2029 使用 JSON 转义；数组顺序保留。Go 导入器与 JS 导出器的结果通过实际 seed 导入测试互相验证。

导入器限定输入 2 MiB、嵌套深度 64，拒绝重复键、非法 UTF-8、未知字段、错误哈希和无效集合/字段。builtin 路径固定为当前三张占位封面、分享 PNG、favicon，不接受任意路径或远端下载。清单与 payload 中素材的哈希/大小须一致。哈希提供可复核完整性和来源记录，不等于数字签名；替换 seed 前仍需审查来源 SHA 与文件清单，不能导入不可信第三方 JSON。

## 显式导入与重复执行

先显式迁移并通过受控 TTY 初始化管理员，再执行 CLI 的 `import-v1`。CLI 读取 `XIAOWORK_IMPORT_PATH`（镜像默认 `/seed/v1.json`）；该路径只用于本地受控命令，不暴露为 HTTP 参数。具体开发栈命令见 [开发说明](V1.1-DEVELOPMENT.md)。

Go 入口为：

```go
contentdata.Import(ctx, db, reader) (contentdata.ImportSummary, error)
```

首次导入取得写锁后检查：管理员已存在、workspace revision 为 0、项目/分类/文档/素材均空。全部字段和媒体引用在同一事务验证并写入，最后记录 provenance、revision 1、完整已校验内容历史与脱敏审计；任何失败都回滚，不留下半套资产或项目。

已有 `content_imports` 时返回原记录与 `alreadyImported: true`，不重复创建历史、不覆盖任何后续编辑，即使再次提供另一份有效 seed 也不会偷偷替换。没有导入记录但已有草稿/媒体或非零 revision 时拒绝，要求人工确认迁移方案；没有“强制覆盖”开关。

该流程只初始化私有草稿。没有生成快照、修改公开 HTML、执行发布 worker 或改变 V1.0 的服务目录。

## 视图、引用和修改历史

`/profile` 与 `/settings` 是逻辑 API 视图，底层仅使用 `workspace_documents.site/profile`。首页简介只存 `siteProfile.introduction` 一份；任一视图 PUT 后另一视图立即读取新简介，同时保留其余字段。`avatarAssetId`、`brandAssetId`、默认/页面分享图与项目封面均登记显式素材引用，拒绝不存在、已软删或不满足公开确认要求的素材。

所有 HTTP 内容写入通过统一 `If-Match` 事务：校验当前 revision → 内容与引用变更 → 递增 revision → 写 `workspace_changes` 的已校验结果及脱敏审计 → 一次提交。缺失版本返回 428，旧版本返回 409；不存在静默覆盖。创建项目另有账户/端点作用域幂等键，同键同请求回放已有结果，同键不同请求返回 409。

项目 description 最多 20,000 字。创建项目的完整编码结果还受既有幂等记录 `response_json` 的 65,536 字符总上限限制，极端 JSON 转义内容超限返回 422 且事务回滚；不能以数据库错误或部分写入处理。普通字段限制仍按 [API 契约](architecture/V1.1-API-SECURITY.md) 执行。

当前 `/dashboard` 只报告实际草稿数量与脱敏近期事件。P6-D 的 current/manifest/HTTP 核验未接入，公开项目数和差异统计明确为不可用；不将最新数据库 release 记录当作实际活动版本。

## 实际验证与后续边界

本轮已实际通过：

- 旧 schema-1 数据升级到 2 后 revision 保留；重复迁移、全部旧 checksum、版本缺口和未知库拒绝。
- 实际导出 seed 的 hash 与 Go 导入一致；三项目真实性字段保持；重复导入不覆盖编辑；篡改/非空库拒绝且无部分内容。
