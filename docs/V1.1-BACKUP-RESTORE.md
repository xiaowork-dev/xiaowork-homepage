# V1.1 一致性备份与灾难恢复

## 原生 Linux 属主修复（2026-11-08）

在原生 Linux 隔离环境，以 root 身份运行宿主操作工具时，`c7edb2f` 的备份实测失败。原因是工具把 root 拥有的 0700 **父目录** bind 到 `/backup`，而维护容器以 UID 10001 运行且去掉了全部 capability，无法进入该目录。Go 端又把 `EACCES` 误报为 "backup destination must not exist"。用同样挂载参数做的探针还证实：`docker volume create` 新建卷的根目录为 `root:root 0755`，加上 `volume-nocopy` 后不会复制镜像挂载点属主，所以恢复到新卷也会失败。Docker Desktop 的 Windows bind 语义掩盖了这两个问题。

修复后的行为：

- 只 bind 新建的备份目录本身（`/backup`），容器输出写到 `/backup/content`。在 Linux 上先核对维护镜像 ID 的 `Config.User` 确为 `10001:10001`，再把**这一个新目录**临时交给 10001；备份完成后归还给操作员。`content/` 保持 10001 所有、权限 0700。
- 校验与恢复前检查 `content/` 属主仍为 10001。复制备份时必须保留属主（例如 `cp -a` 或 `tar --same-owner`），工具不会自动改权限。
- 恢复只对**刚新建的空卷**初始化一次属主：创建但不启动一个不带 nocopy 的维护容器，逐个核对挂载名称和读写属性后移除，再在 Linux 上核对卷根属主为 10001。源数据卷、备份读取和恢复写入仍全部使用 `volume-nocopy`。
- Go 端只在目标已存在时报 "must not exist"；权限不足、父目录缺失等情况报 "backup destination cannot be created: <原因>"。
- 镜像身份、挂载来源、SHA256、SQLite 一致性和维护屏障校验均未放宽。

验收要求：本修复改变了维护镜像源码，六角色必须从新的完整 SHA 重新构建，并在全新独立项目中先验证备份成功，再验证空卷恢复和数据一致性。旧 `acc1` 失败现场（锁和 recovery-required 屏障）保持原样，不在其上重试。

## 备份集合与一致性

`homepage-maintenance` 是独立离线工具，未链接到管理 HTTP API 或发布 Worker。容器无网络、只读根、UID 10001、移除全部 capability、无 Docker Socket 或 SSH/GitHub 凭据。宿主操作工具通过 Docker CLI 编排，要求本地 Docker Engine、Compose 插件及 Node.js 22+；不会连接 SSH/TCP Docker context。

受控停写顺序：独占本站生命周期锁 → 停止本站 API/Worker/api-init → 确认这些容器均未运行 → 检查数据库不存在 queued/running/reconciling 任务 → SQLite `VACUUM INTO` 生成一致副本 → 复制不可变上传和完整发布目录 → 检查副本 → 写逐文件 SHA256 manifest。公开静态 Nginx 可以继续提供旧版页面；管理端和发布操作在备份期间短暂不可用。

不是只复制运行中 `content.sqlite`。即使主数据库尚有 WAL，SQLite 生成的副本仍包括已提交内容。工具检查全部迁移版本/checksum、`integrity_check`、`foreign_key_check`、上传记录与文件大小/SHA、封存快照 SHA、全部历史 release manifest/文件和 current 与数据库成功记录关联；发现未完成任务或损坏即拒绝，必须先完成现有任务对账。

备份包括：

- SQLite：管理员密码哈希、内容/分类/设置、工作区 revision、素材引用、审计、任务和发布历史。
- uploads：全部派生图片，包括仍由草稿、历史内容或备份保护的资源。
- publications：current 相对链接、全部历史公开/预览目录、快照相关 manifest、staging、intent/receipt、锁文件。只允许受控的 `publications/current → releases/rel_*` 符号链接。
- secrets：持久会话密钥。开发验收另外保留独立 authority/TLS，生产不能复用测试 CA。
- manifest：schema、计数、revision、active、历史构建 source SHA/Builder 镜像身份、每个文件和允许链接的清单。
- 独立 `bundle.json`：实际运行的完整源码 SHA、schema、六个镜像 ID（API、Worker、gateway、legacy frontend、publication-static、maintenance），以及运行描述符和内容 manifest 的 SHA256。无需依赖原宿主 `.v11-deploy/current.json` 还原部署描述符。镜像二进制仍须保留在受控镜像仓库或离线归档；备份记录 ID，不会把镜像层打入内容备份。

完整备份目录只有 `bundle.json` 和 `content/`；SQLite、图片、发布目录、secret/authority/TLS 与逐文件 `manifest.json` 均位于 `content/`。校验先检查 bundle 严格字段和双 SHA，再使用 bundle 记录的维护镜像校验完整文件清单与应用状态。SHA 能发现意外损坏，不代替签名或可信离线保管；攻击者若可同时改写所有文件和哈希，仍能伪造备份。

这些文件含密码哈希、会话材料、私有图片和 CA/证书私钥，**不是公开交付物**。默认写忽略目录 `.cache/v11-backups/`，Linux 目录700/文件600；Windows工具限制该专用目录的继承ACL，仅授权当前用户。应将完成校验的备份加密复制到另外的受控位置，并单独保管解密凭据。本版不代管远端备份或加密密钥，不能把本机单份备份当作异地灾备。

加密异地副本的可执行准备、离线密钥与独立签名、验证和恢复演练、RPO/RTO、保留策略及容量告警责任方案见 [V1.1备份运维](V1.1-BACKUP-OPERATIONS.md)。当前没有已确认的外部存储或告警账户，也没有实际执行异地传输；不要将方案文档当成已运行的异地灾备。

## 恢复到独立空卷

1. 保存当前故障现场，不删除或覆盖原数据库/图片/发布卷。
2. 从 `bundle.json` 提取 `runtime.source`、`runtime.schema`、`runtime.images`，构成含 `format: 1` 的版本描述符；准备对应源码和全部六个完整镜像 ID。工具严格拒绝未知/更高schema和迁移 checksum 漂移，不自动降级。恢复无需原服务器的 `.v11-deploy` 目录。
3. 选择从未使用过的独立恢复项目名。该项目不得已有容器、任何目标卷或非空目录。
4. 校验完整备份，创建新卷，复制后再次验证所有状态。恢复最后撤销全部 Session/再认证状态和登录 challenge，管理员密码哈希保留，必须重新登录。
5. 在不同回环端口与独立网络启动恢复栈，通过真实 HTTPS 重新登录，核对 revision、项目、图片、历史、current、前台三页、SEO、资源及 HTTP 证据。
6. 验收成功后才另行安排反代切换；P6-E 不执行真实生产切换。

```bash
node scripts/v11-maintenance.mjs restore \
  xiaowork-homepage-v11-isolated-recovery \
  sha256:<完整已验收维护镜像ID> \
  .cache/v11-backups/isolated-20261028

node scripts/v11-release.mjs deploy \
  --project xiaowork-homepage-v11-isolated-recovery \
  --manifest .cache/reviewed-v11-release.json \
  --restored 1 --topology simulation \
  --http-port 3217 --https-port 3450 --subnet 192.168.244.0/28
```

恢复默认不启用 Worker或发布gate。只有独立本地故障/浏览器验收才可显式增加 `--local-publish 1`。正式 `openresty` 拓扑禁止此参数开启发布。

重复恢复到已有卷直接拒绝。错误不会自动删卷再来，也不会直接覆盖一个仍可用的环境。进程意外退出后，保留未完成备份目录；它不能通过完整 manifest 校验，应选择另一个新目录重做。

发布进程在 current 原子替换前退出可能留下根目录 `current.next.<token>` 相对链接。计划备份和代码更新遇到额外链接仍保守拒绝，**不会自动清理或放宽跟随链接**。本轮新增受信离线工具 `v11-current-repair.mjs inspect/apply`，完整流程见 [单对象残留恢复](V1.1-CURRENT-REPAIR.md)：停本站全部写入者，核对终态任务/intent/receipt、数据库current、所有历史manifest及全部文件SHA，产生SHA绑定的只读计划；仅能移除指定的已证明冗余名称，target历史目录保留，数据库只读。

修复前写并fsync双阶段卷内审计，修复后重核全部SHA及状态。未知/损坏对象、在途任务、计划变化、未完成审计或锁冲突全部拒绝。维护器内部检查失败保留 `operation.lock`，不启动写者；不能删除审计/锁来盲目重试。**本轮9887 stable维护器本身成功后释放了临时锁，随后外层metadata断言失败没有自动新建锁，不能把这一路径写成失败自动留锁，详见[当前修复说明](V1.1-CURRENT-REPAIR.md)。** Linux专项已用真实SQLite/相对链接/kernel lock验证，并包括修复后备份和新空目录恢复；其中静态产物为协议fixture，不冒称六角色真实Nuxt验收。历史817组的实际修复链在全只读SQLite计划阶段失败，后续修复/备份/恢复/更新均NOT_RUN；其当时原库和334文件/链接项保持，见`P6E-final-current-readonly-probe.json`与`P6E-final-current-repair-retention.json`。下方普通备份PASS不能替代这些阻塞。

官方依据为 SQLite `VACUUM INTO` 一致数据库副本与WAL文档；当前工具额外核验项目已冻结的schema和资源，不仅依靠SQLite单文件完整性。
