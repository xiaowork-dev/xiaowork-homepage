# V1.1 最终组故障注入测试计划

- 日期：2026-11-08（Asia/Shanghai）
- 状态：**已执行**（2026-11-08），全部用例最终通过，结果与发现的缺陷见[故障注入交付](deliveries/20261108-v11-fault-injection.md)。
- 对象：运行镜像 `b1080eb065490fe8d6d5afe53fd419861f09e324`，宿主工具 `336db772e10d6b562eaffbfbb03c41b60f327c40`
- 依据：历史 817 组的 [12 项真实故障矩阵](P6E-FAULT-TESTS.md)。旧成绩不计入最终组。

## 1. 目标

在最终组上验证以下情况发生时，系统能**失败即关闭**、**公开站点不被破坏**、**状态可以对账和恢复**：

- 进程崩溃、超时、资源耗尽；
- 发布原子切换的每个边界被打断；
- 数据库事务被打断、核验服务不可用；
- 维护操作被打断。

另外补上历史上从未完成的一条链：`current.next` 修复 → 备份 → 空卷恢复。

PASS 只表示安全行为符合预期，不表示故障能自动恢复或服务始终可用。凡是需要操作员干预（重启服务、恢复权限等）的步骤，都会如实记录。

## 2. 安全边界（执行时严格遵守）

| 项目     | 边界                                                                                                                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 位置     | 只在主服务器 `/opt/xiaowork-homepage-v11-test` 下的新项目中执行，只绑回环端口                                                                                                                        |
| 故障对象 | 只对本次新建测试项目的容器发送 SIGKILL 或重启；chmod 和写满空间只作用于本项目的数据卷，或 Worker 容器自带的 `/work` tmpfs（768 MiB）                                                                 |
| 禁止事项 | 不重启 Docker 引擎或宿主机；不填充宿主磁盘；不修改防火墙、OpenResty、V1.0、其他项目、正式域名；不执行全局清理；不删除锁或 recovery-required；不在已有的失败现场上重试                                |
| 测试镜像 | 从 b1080eb 正式镜像派生出测试专用的 API/Worker/数据工具镜像，tag 为 `xiaowork-homepage-v11-faulttest-*`，只用 `p6e_fault` 构建标签编译检查点。**它们不会写进任何发行描述符**；正式镜像不包含故障开关 |
| 资源     | 新增 2 个项目：ft-sim（模拟拓扑，占 2 个默认池网段）、ft-prod（生产拓扑，占 1 个）。开始前确认默认池余量至少 4 个；完成后停掉未加锁的项目来释放                                                      |
| 失败处理 | 任何一项结果不符合预期，就停止后续用例，保留现场并报告；不为了通过而放宽校验                                                                                                                         |

## 3. 故障矩阵

### A. 发布链路（ft-sim，测试 API/Worker 镜像）

| #   | 故障                       | 注入方式                                                                                     | 预期安全行为                                                                  |
| --- | -------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| A0  | 正常基线                   | 真实 Nuxt 构建与发布                                                                         | 成功；current、manifest、HTTP 一致                                            |
| A1  | Nuxt 编译失败              | 测试 Worker 镜像中挂入固定的非法 Vue 源码                                                    | 任务 failed；旧站、草稿、current 都不变                                       |
| A2  | 构建超时                   | 固定的 `build:before` 延迟 hook，等满 10 分钟                                                | 进程组被终止，任务 failed，旧站不变（实际耗时约 10 分钟）                     |
| A3  | 构建中 Worker 被杀         | 观察到 Nuxt 进程后 SIGKILL Worker                                                            | 租约到期后由同一任务对账并 failed，不重复构建，旧站不变                       |
| A4  | 原子切换前 Worker 被杀     | 停在 `before-current-rename` 检查点后 SIGKILL                                                | current 不变；留下 `current.next.*`；新任务被阻断                             |
| A4b | **current.next 修复链**    | 对 A4 留下的现场依次执行 inspect-current → 修复单个链接 → 一致性备份 → 空卷恢复 → 一致性核对 | 只删除这一个链接，有审计；历史和 SHA 不变；备份和恢复成功（**历史上未完成**） |
| A5  | 原子切换后 Worker 被杀     | 停在 `after-current-rename` 后 SIGKILL                                                       | 同一任务通过 intent、current 和 HTTP 对账完成或恢复，不误报成功               |
| A6  | SQLite 成功事务中 API 被杀 | 测试 API 的固定触发点，在成功状态 UPDATE 时 SIGKILL                                          | WAL 回滚；任务不提前显示成功；重启后对账一致                                  |
| A7  | 任务进行中 API 重启        | 真实 Nuxt 构建过程中重启 API                                                                 | 静态站保持；任务对账后结果一致                                                |
| A8  | 切换时静态服务重启         | current 切换后重启 publication-static                                                        | 重启后版本与资源一致（不声称零停机）                                          |
| A9  | 历史版本损坏               | 暂时移走历史 release 的 index.html（只在本项目的卷内），测试后还原原字节                     | 恢复被拒，当前版本保持                                                        |
| A10 | 核验服务不可用             | 把 API 的 verifier 指向同网内未监听的端口（测试配置）                                        | 不伪报成功，保持阻断；恢复后同一任务核验通过                                  |
| A11 | 恢复再次失败               | 把本项目发布卷根目录改为 0500，造成两次真实 EACCES，再恢复权限                               | 新任务返回 409；人工修复后同一任务成功，错误字段清空，失败审计保留            |
| A12 | 构建临时空间满             | 只写满 Worker 自带的 `/work` tmpfs                                                           | 内核返回 ENOSPC，任务 failed，旧站不变，宿主磁盘不受影响                      |

### B. 生产 gate 与维护（ft-prod，正式镜像，生产拓扑）

| #   | 故障                   | 注入方式                                                                  | 预期安全行为                                                                         |
| --- | ---------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| B1  | 构建中撤销授权         | 发布任务正在构建时执行 `revoke-publishing`                                | 进行中的任务完成或进入对账；新任务立即被拒；排队任务在领取时失败                     |
| B2  | 发布进行中执行 update  | 构建中执行 `update`                                                       | 维护屏障先排空进行中的任务，再停写和备份；不中断切换；更新后发布关闭                 |
| B3  | 备份过程中运维进程被杀 | 对宿主上的 `node v11-release.mjs backup` 进程发送 SIGKILL（只杀这个进程） | `operation.lock` 和 recovery-required 保留，后续操作被拒，API 保持 503，公开站点正常 |
| B4  | update 候选启动失败    | 候选组使用一个缺失固定可执行文件的测试 gateway 镜像                       | 自动恢复旧服务并通过 HTTP 复验；数据不变；锁按协议释放                               |

### 不在本计划范围内（需要另行评估）

- 宿主机重启、Docker 引擎重启、断电：会影响同机全部业务，不做。
- 真实磁盘写满、物理存储故障：会影响宿主，不做（A12 只覆盖 tmpfs 层面）。
- 发布入队时的存储容量 507 门槛：需要调整阈值配置，本轮不做。

## 4. 实现准备（批准后进行，提交到功能分支）

1. **测试镜像夹具**：在 `scripts/fixtures/p6e-fault-worker.Dockerfile` 中，把依赖本地 `p6b-test` 镜像的构建阶段改为固定的 `golang:1.27.3-alpine`，基础镜像参数指向 b1080eb 正式镜像，并在报告中记录实际的测试镜像 ID。正式 Dockerfile 不变。
2. **API 驱动的控制器** `scripts/v11-fault-acceptance.mjs`：取代依赖 Playwright 和 Docker Desktop 的旧控制器，复用本轮的登录、预览、发布、对账辅助逻辑。每个用例记录任务、current、SQLite 摘要、manifest/页面哈希、HTTP 结果和人工干预，输出一份 JSON。
3. 控制器只接受固定的用例名，不接受任意命令或路径；只操作名称以 `xiaowork-homepage-v11-ft` 开头的项目。

## 5. 预计影响与耗时

- 构建 3 个测试镜像约 2 分钟；A2 需要等满 10 分钟；全部用例预计 1.5～2 小时。
- CPU 在构建期间短时占用；内存每个项目约 30 MiB（构建时 Worker 最多 3 GiB 上限）。
- 磁盘：测试镜像和数据约 1～2 GiB（当前使用率 14%）。
- 不影响 V1.0 和其他业务；结束后再做一次影响核对。

## 6. 回退与清理

- 每个用例都只针对新项目；出现异常就停止，保留现场。
- 完成后，用 `v11-release stop` 停掉未加锁的测试项目（保留数据卷）。加锁的现场保留，等待用户决定。
- 测试镜像保留（不删除），清理需要用户另行批准。
