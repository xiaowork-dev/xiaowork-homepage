# V1.1 SQLite 数据与发布一致性设计

日期：2026-10-26。阶段：P6-A 可执行设计初稿。对应 [001_initial.sql](../../backend/migrations/001_initial.sql)。本阶段仅定义表、约束和后续实现契约；没有实现管理 CRUD、登录、上传、发布 worker 或恢复流程，也没有在现有服务器运行迁移或修改 V1 数据。

## 运行边界与迁移

Go API 是 SQLite 的唯一拥有者。计划基线为 Go 1.27.3、`modernc.org/sqlite v1.61.0`，确切驱动和 SQLite 核心版本由实现阶段记录。发布 worker 不挂载数据库，通过专用 Unix socket 向 API 领取已封存快照、提交状态；其写权限仅限发布根，uploads 只读。API 另有发布根只读挂载，用于自己读取 current、manifest 和 receipt 核验，不只信任 socket 回报。公共静态服务不接触 SQLite、会话、草稿、原始上传文件或后台配置。完整流程以 [发布与恢复设计](V1.1-PUBLISHING.md) 为准。

迁移由显式 CLI 调用，runner 在事务中执行本文件并记录自己拥有的 `schema_migrations(version, applied_at, checksum)`；checksum 绑定嵌入迁移的准确字节，同 version 的 SQL 漂移必须拒绝，不能仅比较最大版本号。SQL 不含事务控制、PRAGMA、业务种子或账户。`serve` 只接受已存在且 schema 版本为 1、checksum 匹配的数据库；不在启动时隐式建库、创建默认管理员或升级 schema。P6-A `/healthz`、`/readyz` 与管理 API 的关闭状态不代表认证已经实现，P6-B 才开放实际能力。

每个连接均须由 API 配置外键和合理 busy timeout；连接池不能只对随机一条连接设置 PRAGMA。是否启用 WAL 及 synchronous 策略须在 P6-B 负载、故障和备份测试后确认。SQLite 数据位于本机持久化目录，不放 NFS/其他网络文件系统；启用 WAL 时核对运行时 `sqlite_version()` 含官方 WAL-reset 修复，不能仅按 Go 模块号或宿主 sqlite3 版本判断。

所有 `*_at` 为 Unix 秒，UTC，整数，由可信服务生成；本版不使用 SQL 自动时钟。ID、slug、状态、散列格式及基本长度由数据库约束，字符规范、URL、JSON 字段结构、时间逻辑和业务权限由 API 再验证。SQLite 中的 JSON 有效不代表它满足公开投影或业务 schema。

| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |

| `sessions`                                       | 仅存随机 session token 与派生 CSRF token 的 SHA-256 散列、到期/撤销时间和凭据版本；不存原始令牌。服务检查过期、撤销及密码版本，数据库不会自动淘汰会话  |

| `workspace`                                      | 仅允许一行，全局 revision 用于全部草稿的并发控制；不自动种子初始化                                                                                     |
| `workspace_documents`                            | `site`/`profile` 的 JSON 对象；字段白名单、字符串数组、公开范围、SEO origin 和联系方式由运行时 schema 校验                                             |
| `project_categories`                             | 稳定 ID、唯一 slug、名称和排序；被项目引用时禁止删除                                                                                                   |
| `project_drafts`                                 | 项目草稿、分类、简介、纯文本 description、标签数组、状态、精选/占位/visible、归档时间与确认外链；保存不意味着发布                                      |
| `assets`                                         | 已验证素材的不可变元数据：受限相对 key、散列、媒体类型、大小和尺寸；用户上传只允许受支持的栅格格式，SVG 仅允许受控内置素材                             |
| `project_draft_assets` / `document_draft_assets` | 草稿到素材的显式外键；阻止删除仍在草稿使用的素材。JSON 中的素材字段与这些引用需在同事务更新                                                            |
| `snapshots` / `snapshot_assets`                  | 不可变公开 JSON 投影、revision、投影版本、内容散列和媒体引用；先在事务内组装，再封存                                                                   |
| `publish_jobs`                                   | publish/preview/rollback 幂等请求、固定 snapshot、目标 release、worker 租约、status/phase 和本次对账证明；全站至多一个 queued/running/reconciling 任务 |
| `releases`                                       | publish/preview 构建产生的不可变目录、快照、模板源码 SHA 与 manifest 散列；preview 有 expires_at，publication 无 TTL；不保存 active 或旧对账证明       |
| `audit_events`                                   | 追加式脱敏审计，记录行为、对象、结果和受限 metadata；不记录密码、哈希凭据、会话/CSRF token、完整请求体或内部路径                                       |

单管理员模式没有多角色/RBAC 或多租户承诺。未来增加账号或功能须通过审查后的 schema 迁移扩展，不私改已发布的 001。

## 登录挑战、再认证与幂等

`login_challenges` 将预登录 Cookie 和返回的 login nonce 分别散列后关联，数据库限制有效期不超过创建后300秒。登录尝试以带 Cookie/nonce/未消费/未过期条件的原子更新消费 challenge，再执行密码验证，密码错误也不能复用。触发器禁止重置已消费记录。单来源10个、全局1,000个未使用 challenge 配额和有界过期清理由 API 在事务及限速边界执行；字段存在不表示抗重放/限速已经实现。CLI 密码重置须撤销会话、challenge 及再认证状态。

`sessions.last_seen_at` 可用于一般活动观测，`last_interactive_at` 只由真实已认证交互更新；任务轮询不延长30分钟空闲期。`expires_at` 是绝对截止，不被再认证延长。`reauth_until` 只绑定当前会话、不得晚于绝对截止；敏感操作按服务器时间验证最近5分钟再认证，拒绝客户端布尔字段替代。注销/改密/重置使会话及其再认证能力一起失效。CSRF 原始值的返回/派生或轮换策略须与 [API 安全设计](V1.1-API-SECURITY.md) 一致，不能假设能从散列恢复原 token。

`idempotency_records` 的主键为账户、规范端点和客户端 `Idempotency-Key`；请求哈希不是主键的一部分，才能拒绝同键不同请求。客户端键长度16～128，只允许字母数字与 `-_`。同键同请求返回已保存的非敏感结果，同键不同请求409；记录至少保存24小时。API 在创建资源/任务及 revision 的同一事务插入完整幂等结果，不先提交一个无结果的半完成条目。response_json 不含 Cookie、会话/CSRF/登录 nonce、密码或内部路径。端点必须是服务端规范枚举，不接受任意 URL 作为作用域。

`publish_jobs.idempotency_key` 是服务端派生的账户/端点作用域标识，不能直接写原始 HTTP 键，否则同一个合法客户端键在 preview 与 publish 端点会错误冲突。幂等记录和任务记录的对应、24小时清理及并发重试由 P6-B 事务测试覆盖；schema 本身不实现 HTTP 去重响应。

## 草稿并发与运行时验证

P6-B 的每次草稿变更必须在同一事务检查客户端预期 revision、执行内容与素材引用变更、递增 `workspace.revision` 并写审计。revision 不匹配返回冲突，不能静默覆盖。API 先验证完整对象，再写入；不得将未验证 JSON 当成站点配置直接导出。SQL 不使用触发器自动增加 revision，避免一次复合编辑多次递增或漏掉跨表业务事务；该契约由 API 及并发集成测试保证。

`demo_url`、`repository_url` 缺失使用 SQL NULL，不填 `#` 或示例站点。API 复用已有 HTTPS/正式 origin 规则，并拒绝凭据、危险 scheme 及伪造素材路径；数据库长度限制不能替代 URL 解析。状态 `unconfirmed`、占位封面、空技术栈保持独立，不根据素材存在就推断项目已上线。ERP 素材仅在确认公开且脱敏后接入。

`description` 为纯文本，P6-B 不加入任意 HTML/Markdown 执行能力；输出由 Vue/构建器正常转义。`visible` 控制是否进入公开快照，`archived_at` 标记草稿归档；数据库要求归档时 `visible=0`。API 公开投影只选 `visible=1 AND archived_at IS NULL`，隐藏/归档操作仅修改草稿和 revision，不直接改变已发布页面；恢复归档需要显式草稿操作与再次发布。

公开 JSON 必须使用独立的白名单 DTO，不能直接序列化数据库模型。个人/站点 JSON 的密码、内部标记、草稿备注、用户资料和存储路径不进入投影。模板以结构化文本渲染；不提供任意 HTML、脚本或服务端代码配置。

## 素材与不可变快照

素材内容先在临时位置按大小、文件签名、解码尺寸和允许格式验证，再以生成的不可变 key 落盘；不能信任文件扩展名或原文件名。数据库记录只在文件完成写入后创建。路径还需在 Go 中规范化并确保落在指定根内，防符号链接和路径穿越；SQL 的字符检查不是文件系统安全沙箱。

`assets` 只表示不可变内容身份和文件事实；`asset_metadata` 单独保存 alt、显示名称、公开使用确认人/时间/说明和 deleted_at。P6-B 上传登记时同事务建立两行，PATCH仅修改 metadata 并递增 workspace revision。公开确认不等于图片解码成功，撤销确认也不会自动从历史发布/CDN撤回媒体；敏感资料撤回需独立授权流程。

软删除时仍被项目/站点草稿或快照引用的素材返回409；触发器为首次软删除增加引用保护。API 还必须拒绝给已软删除素材建立新引用，冻结投影时检查 metadata 存在、未删除及上传素材已确认公开，并把该次 alt/确认和媒体散列冻结进快照。修改 metadata 不改旧快照、文件字节或旧URL。DELETE不执行物理文件GC，备份/历史release引用仍需另外保护。

发布快照采用一个短事务：读取一致的 workspace revision → 构建并验证公开投影 → 插入未封存 snapshot → 插入完整媒体引用 → 写 `sealed_at` → 创建 queued job → 提交。素材对象及其散列不可变，因此 worker 随后复制只读素材时不会读取到同 key 的新内容。内容哈希由 API 对约定的规范 JSON 字节计算；不假定 SQLite `json()` 等同跨语言 canonical JSON，规范和 golden fixtures 在 P6-B 固定。

触发器禁止修改 snapshot 内容、重复封存、删除 snapshot，以及封存后追加/删除/修改媒体引用；job 仅能引用已封存 snapshot。所有引用素材受外键删除保护。未封存行不得在上述事务外提交；失败通过调用者事务回滚，不用中途提交的半成品表示任务进度。保留历史快照会阻止对应素材回收，这是本版有意的安全默认；后续保留策略、受控删除迁移及离线备份规则另行设计。

## 发布任务、文件系统指针与对账

`kind` 区分 `publish/preview/rollback`。`status` 使用 `queued/running/reconciling/succeeded/failed/cancelled` 表示队列和终态；`phase` 使用 `building/validating/prepared/activating/recovery_required` 细分正在执行或对账的阶段，排队和终态为 NULL。发布设计图中的 building 等节点对应 phase，而非新增 status。`recovery_required` 必须配合 `status=reconciling`，继续持有全站唯一未完成任务槽，不能在结果未知时启动第二个任务。预览也串行复用该槽，部分唯一索引包括 queued，避免已有排队任务后仍再次插入。

这些是后续状态机的存储设计，不是本阶段已实现的操作。API 须通过受影响行数校验的条件更新领取任务、推进 status/phase、续租及校验租约 token；原始租约 token 不落库。过期租约不得立即重跑并盲目覆盖 current，先检查任务目录和现有 manifest，再决定继续对账或失败。worker 不提供任意命令、宿主路径或 Docker 操作能力。成功/失败/取消的历史任务不可修改，重试产生新的受审请求，不重置历史 proof。

worker 在发布根内生成独立候选目录，验证模板源码版本、快照/素材散列、HTML/SEO 与必要 smoke。发布根和 current 临时指针必须位于同一文件系统；只有产物完整且持久化后才原子切换 current manifest，并按实现要求 fsync 文件与父目录。具体文件布局和持久化故障测试在发布实现阶段完成。

SQLite 事务与文件系统切换**不构成一个跨系统原子事务**。实际 active 以文件系统 current 指针及目标 manifest 为依据；数据库不设置一个可能先于文件系统成功的 active 标志。准备激活时 API 生成本次 `activation_token_hash`，worker 在受限 receipt 中记录对应激活证明。重启后和回调时，API 自己通过只读发布根读取 current、manifest、receipt，核对本次 job、activation token、release ID、snapshot、模板版本和散列，并完成 HTTP 核验。不能只听 worker 的 socket 成功消息。

完成 reconciliation 后，API 在单个条件更新中从本次 `status=reconciling` 转为 succeeded，同时填入该 job 的 `reconciled_release_id`、`reconciled_at` 和 `reconciliation_receipt_sha256`，设置 completed_at 并清空 phase。触发器禁止在其他状态提前写 proof、禁止缺 proof 成功、禁止以别的构建任务的 release 冒充本次 publish/preview 结果。SQL 无法读取文件系统，仍不能替代 API 实际核验或保证回报真实。历史 job 的成功时间不能当作新任务已经激活的依据。

current 指针若与数据库不一致，先按实际文件系统事实恢复记录、保存审计，再放行下一次任务。manifest 损坏、引用未知 release 或散列不符时保持 `reconciling/recovery_required`，不伪造 success。失败后的旧版恢复也须核验 current 和 HTTP 后才能把本次任务终结为 failed。激活前旧版未改变的构建失败可直接 failed。此恢复协议及“切换后未回写数据库就崩溃”等断点须在 P6-D 实测。

### 草稿预览与 TTL

preview job 使用相同的 sealed snapshot 和固定构建器，独立生成私有 preview 目录，`releases.kind=preview` 且 `expires_at` 必填。API 对预览结果的当前任务 manifest/receipt 完成核验后写本次 proof 和 succeeded；这里的成功只表示受鉴权预览准备好，绝不切换 current，也不设置 activation token。所有 HTML/chunk/图片请求均需鉴权、no-store、noindex，到期拒绝访问。

过期 preview 文件可由受限 worker 在确认没有 current 引用后按受控路径清理，但 immutable release 元数据保留历史记录；`expires_at` 不是该目录永久存在的承诺。预览目录不能直接提升为 publication，正式发布必须按正式路由/资源前缀重新构建。具体 TTL、配额和安全清理在后续实现阶段测试。

### 内容回滚

rollback 是新的独立 job，`target_release_id` 引用已经有成功激活记录的 publication，snapshot_id 固定为该目标快照；preview 不能作为回滚目标。它不新增物理 release 目录或复制 artifact row，不重编译旧内容，不改草稿、账户或数据库历史。

API 先核验目标完整性/兼容性，沿同一 prepared → activating → 实际 current/HTTP 对账流程执行。只有该 rollback job 自己的新 proof 指向准确 target 才能成功，不能使用目标 release 原来的成功 job 时间。数据库通过外键/触发器限制目标类型、既往成功记录及本次 proof 关联，文件仍完整和当前激活结果由 API 的只读文件系统核验保证。

## 备份、恢复与删除

活动 SQLite 使用驱动支持的 Online Backup API 或 `VACUUM INTO` 生成一致快照；不直接复制仍在写入的单个 `.db` 主文件。数据库备份、素材清单和不可变发布目录组成一个带版本、schema、散列、时间的备份集合；敏感备份仅在受限项目外位置保存，不能进入 Git、公共静态根或公开下载路径。

恢复到隔离目录/数据库后先检查完整性、外键、schema、素材散列及 current manifest。程序镜像回滚只有在 schema 兼容时允许；恢复旧数据库可能丢失后续编辑，应先保留当前快照并明确恢复点。不要自动执行破坏性 down migration、删除卷、清空库或全局 Docker 清理。审计与发布记录当前禁止普通删除，容量/合规保留策略须另行设计。

P6-A 不宣称备份恢复、账户安全、worker 租约或原子发布已经验证。P6-B 至少增加迁移约束、鉴权/CSRF、限速、revision 冲突与不可变引用保护测试；P6-D/E 按 [发布设计](V1.1-PUBLISHING.md) 完成任务串行、preview/rollback、旧 proof 拒绝、任务租约、重启对账、真实故障注入和备份恢复演练。既有 node-forge high 风险和公网未放行状态独立保留，不因新增 Go/SQLite 解除。
