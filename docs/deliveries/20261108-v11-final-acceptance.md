## 3. 本轮发现并修复的缺陷

**回退或更新后，残留的已停止 Worker 会阻塞后续所有生命周期操作**（提交 `336db77`）

- 现象：项目在授权期间运行着 b1080eb 的 Worker。更新到 9e3d4db 后，候选版本按设计以发布关闭状态启动，但旧 Worker 容器只是被停止，并没有被移除。下一次 `rollback` 在核对镜像身份时，把这个已停止的容器也算了进去，报 `Actual project image differs from recorded release descriptor` 并保留锁。`backup` 也会因为同样的原因被阻塞。
- 原因：上一轮"更新/回退后自动关闭发布"的实现，没有清理之前发布配置留下的 Worker 容器。
- 修复：发布关闭的配置在 `start()` 时，只移除本项目**已停止**的 Worker 容器（它是无状态的，数据在数据卷里）；如果 Worker 仍在运行，就拒绝执行。新增 2 个单元测试，分别覆盖"移除已停止的"和"拒绝运行中的"。
- 验证：fin5 上的更新 → 回退 → 回退后备份 → 再次授权全部通过。失败现场 fin4 保留。

## 4. 运维层面的发现

1. **宿主机本地限速桶与生命周期探测共用**：fin3 上先跑了 B6 的对照用例（宿主机发出、不带 `X-Real-IP` 的请求连续申请 10 个登录挑战），约 33 秒后执行授权，授权流程里的 HTTP 探测拿到了 429。授权按设计保持关闭并保留锁（fin3 现场保留）。在正式环境中，OpenResty 会为每个请求设置 `X-Real-IP`，这个桶只有运维工具会用到；但运维人员在宿主机上手动大量请求管理接口之后，应等 5 分钟再执行 deploy/update/authorize。
2. **Docker 默认地址池耗尽**：每个模拟拓扑项目会自动占用 2 个默认池网段（edge、isolated），生产拓扑项目占用 1 个。本机默认池里 172.17～31 都已被原有业务占用，192.168.0.0/16 一共只有 16 个 /20 网段。测试项目累积到 14 个后，新项目报 `all predefined address pools have been fully subnetted`。这会影响同机其他业务新建网络，已在发现后立即停掉 9 个已完成验收的测试项目来释放（数据卷保留）。**正式部署 V1.1 时应只保留一个项目**；如果需要长期同机运行多个，建议后续把 edge/isolated 网段也固定下来，或者由运维评估配置 daemon 的 `default-address-pools`（这属于全局配置，需要单独授权）。
