## 3. 发现并修复的产品缺陷

### 缺陷 1：残留的 current.next 链接会导致项目永久无法备份（修复 `61b7b32`）

- **现象**（b1080eb，A4/A4b）：切换前崩溃留下 `current.next.*` 后，API 仍然接受新的发布任务。新任务成功后，当前版本随之变化，受审修复工具因为"失败任务的上一个版本 ≠ 当前版本"而一直拒绝（`failed task has uncertain active state`）。同时，一致性备份只允许 `publications/current` 这一个符号链接，所以**从此再也无法备份**，只能人工动文件。
- **修复**：没有进行中的任务、但存在 `current.next.*` 时，发布和恢复返回 503 RECOVERY_REQUIRED，提示先执行受审修复；预览不改变当前版本，继续允许。新增 publishfs 列举接口（含 Linux 测试）和 HTTP 测试；控制器把这一点作为断言。
- **复测**：ft-sim2 上 A4 和 A4b 全部通过。

### 缺陷 2：候选失败并已安全恢复后，仍然锁定管理 API（修复 `a6f7e56`）

- **现象**（B4）：update 已经恢复旧服务、两套检查器都确认数据未变、HTTP 复验通过、旧的 current 记录也已恢复，但依然保留 `operation.lock`，屏障停在 recovery-required，管理 API 返回 503。这与运维文档"已验证恢复后才解除阻断"的约定不符。
- **修复**：记录"已验证的安全恢复"状态，这种情况下释放本命令自己的锁并完成屏障；命令仍以非零退出码报告失败。无法确认恢复的路径和父链仍保持保护。新增单元测试。
- **复测**：ft-prod2 上 B4 通过，随后备份成功。

## 4. 测试控制器自身的问题（已修复，失败记录保留）

1. 初始化阶段在创建报告对象之前就记录事件，导致控制器崩溃（`4ad6c78`）。
2. A12 用例写满 tmpfs 后没有重建 Worker，下一个用例 api-restart 的构建因为"临时空间不足"被产品拒绝（这一拒绝本身是正确的安全行为），于是被误判为失败。失败记录保留为 `api-restart-harness-fail-1.json`；修复为每个用例结束后都重建 Worker（`72ca581`）。
3. 有一次命令链在 lint 失败后仍然执行了提交，推送了一个 lint 不通过的提交（`f86b2bc`），随即由 `408db44` 修正。
4. B2 中 update 之后发布已关闭，`/jobs/{id}` 按设计返回 503，所以改为用测试数据工具只读查询数据库来确认任务状态。

## 5. 运维观察

- **只读修复检查失败也会锁住项目**：`v11-current-repair inspect` 走受保护的独立 CLI，检查失败会保留锁。`review` 解锁需要重新检查成功，所以在缺陷 1 修复之前，ft-sim 会一直处于锁定状态。缺陷 1 修复后，正常情况下不会再出现这个前提失效的场景；但运维仍应注意：修复检查只能在"崩溃后、尚未发布新版本"的状态下执行。
- **Worker 临时空间保护**：`/work` 不足时会直接拒绝构建，旧站不受影响（A12 和 api-restart 的首次运行都观察到了）。
- **Docker 地址池**：保留的失败现场目前占用 11 个默认池 /20 网段（再加原有的 1 个，共 12 个，上限 16 个），**只剩 4 个**。这会影响同机其他业务新建网络，建议尽快清理（见第 7 节）。

- 发布入队时的存储容量 507 门槛：需要调整阈值，本轮不做。
