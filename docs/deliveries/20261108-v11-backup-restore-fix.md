## 1. 备份失败的精确原因

| 项目     | 实测                                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 失败命令 | `node scripts/v11-release.mjs backup --project xiaowork-homepage-v11-acc1 --backup <新目录>`（root 运行，运行组 c7edb2f），退出码 1               |
| 失败步骤 | 维护容器 `/homepage-maintenance backup -target /backup/<名称>/content` 退出码 1。容器配置：UID 10001、只读根、去掉全部 capability、无网络，非 OOM |
| 完整日志 | `maintenance refused: backup destination must not exist`                                                                                          |
| 挂载     | 宿主上新备份目录的**父目录**（`root:root 0700`）以可写方式 bind 到 `/backup`；6 个源卷以 nocopy 方式可写挂载                                      |
| 根因     | UID 10001 没有权限进入 root 拥有的 0700 目录，`os.Mkdir` 返回 EACCES；Go 端把所有 Mkdir 错误都报成"目标已存在"                                    |
| 已排除   | 挂载 Source 与请求路径完全一致（路径身份和规范化在原生 Linux 上都正常）；挂载确为可写；磁盘、inode 充足；源卷属主为 10001                         |
| 同类问题 | `docker volume create` 新建的卷根为 `root:root 0755`，nocopy 不复制镜像挂载点属主，导致恢复到新卷也会失败（探针已实测）                           |

Docker Desktop 的 Windows bind 语义不执行 Linux 属主检查，因此这两个问题此前一直没有暴露。

修复后在恢复环节又发现**第二个缺陷**：`guardedOperation` 的独立 CLI 分支（`v11-maintenance.mjs inspect|backup|restore`）创建锁后没有登记归属，标记里也缺少 `owner` 字段，结果被自己的锁拒绝（`Persistent operation.lock blocks new tasks`）。该入口在动任何卷之前就失败并保留了锁，属于失败即关闭，没有造成数据风险。
