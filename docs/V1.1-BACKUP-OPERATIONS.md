# V1.1 备份运维、异地加密副本与演练

更新：2026-10-28，Asia/Shanghai。本文是本项目的可执行运维方案；本轮没有连接正式服务器、购买外部服务、发送告警或创建异地账户。现有一致性备份与新空卷恢复的实现和验收见 [备份恢复说明](V1.1-BACKUP-RESTORE.md)。

## 本地备份和异地副本

本地备份是维护工具在受控停写后生成的完整 `bundle.json + content/` 集合，采用 SQLite `VACUUM INTO`，覆盖已提交 WAL、上传、内容快照、发布历史、manifest/current 及必要的账户/秘密数据。它可以快速恢复误操作，但与 Docker 卷位于同一主机时，不能抵御主机丢失、勒索、磁盘损坏或管理员权限被盗。

异地副本必须位于另一个故障域，并在离开备份主机前完成加密。可选目标是用户控制的另一台机器、离线移动介质或之后明确选择的对象存储；尚未确认任何目标、账户、容量、保留锁或凭据。只有收到目的地确认、实际复制并从该副本完成恢复演练后，才能声称异地灾备已部署。不能把本地第二个目录或同一 VPS 的第二个 Docker 卷称为异地。

建议采用 3-2-1：正式持久卷、经验证的本地备份、另一故障域的加密副本，至少两种存储介质，其中一份可离线或不可变。该策略目前为待用户确认的目标，不冒充已实现的基础设施。

## 加密和来源认证

建议使用官方 `age` 的 X25519 接收者模式加密和独立 OpenSSH Ed25519 签名。维护主机只保存公开 recipient 和签名验签公钥；解密私钥留在独立离线保管处。不要使用本站管理员密码、会话 secret、GitHub Token 或服务器 SSH 登录密钥作为备份加密密钥。也不要把秘密放入命令参数、环境变量、shell history 或仓库。

使用前在可信运维机安装经审核的官方 age 版本并核对发行校验/签名，记录版本、二进制 SHA256 与批准来源。当前开发主机未安装 age；本轮未下载未知二进制或把未实际执行的加密演练记为通过。以下 Linux 命令的前提是已安装可信 `age/age-keygen`、OpenSSH、GNU tar/coreutils；目录均由操作者替换为专用绝对路径，不能直接复制占位路径执行。

### 一次性离线密钥准备

在离线且磁盘加密的运维机执行；`age-keygen` 的输出文件是私钥，权限为 600，仍须使用受控加密介质和独立备用副本保护。Ed25519 签名密钥使用工具的交互式口令提示，不使用 `-N` 传明文口令。

```bash
umask 077
mkdir -m 700 /OFFLINE-KEYS/xiaowork-backup
age-keygen -o /OFFLINE-KEYS/xiaowork-backup/recipient-key.txt
age-keygen -y /OFFLINE-KEYS/xiaowork-backup/recipient-key.txt > /OFFLINE-KEYS/xiaowork-backup/recipients.txt
ssh-keygen -t ed25519 -f /OFFLINE-KEYS/xiaowork-backup/signing-key -C xiaowork-backup
```

只将 `recipients.txt` 和签名公钥的受信副本带到需要的工作站。`allowed_signers` 文件的身份名为 `xiaowork-backup`，后跟该独立签名公钥；公钥指纹由操作者经另一渠道核对。备份服务器不需要解密密钥。签名操作可以在离线运维机对传入的哈希清单执行，避免把长期签名私钥放在 VPS。

### 每次备份及加密

1. 确认本站没有未对账任务或生命周期锁；如存在 `current.next.*`，按专用恢复流程核对，不批量删除或跳过完整性检查。
2. 按已验收源码和 maintenance 镜像 ID 执行 `v11-release.mjs backup`，先通过 `v11-maintenance.mjs verify`。备份期间管理端停写；公开静态服务可以继续提供当前版本。
3. 使用新的专用输出目录、`umask 077`，将完整备份集合归档。不能只归档数据库主文件。tar 默认不跟随链接，禁止 `--dereference`；归档前维护工具已严格验证允许的相对链接。
4. 使用公开 recipient 加密；清单只记录密文 SHA256、字节数、备份时间、运行源码、schema、当前版本和密钥编号，不写管理员密码、私钥或完整账户数据库。

```bash
# 所有示例路径均由操作者替换；输出目录必须新建，不能覆盖已有副本。
umask 077
mkdir -m 700 /PRIVATE-EXPORT/backup-YYYYMMDDTHHMMSSZ
tar --format=pax -C /VERIFIED-BACKUP-PARENT -cf /PRIVATE-EXPORT/backup-YYYYMMDDTHHMMSSZ/content.tar BACKUP-DIRECTORY
age -R /PUBLIC-RECIPIENTS/recipients.txt -o /PRIVATE-EXPORT/backup-YYYYMMDDTHHMMSSZ/content.tar.age /PRIVATE-EXPORT/backup-YYYYMMDDTHHMMSSZ/content.tar
cd /PRIVATE-EXPORT/backup-YYYYMMDDTHHMMSSZ
sha256sum content.tar.age > SHA256SUMS
```

5. 在持有独立签名密钥的离线工作站签署 `SHA256SUMS`：

```bash
ssh-keygen -Y sign -f /OFFLINE-KEYS/xiaowork-backup/signing-key -n xiaowork-backup SHA256SUMS
```

6. 只复制 `content.tar.age`、`SHA256SUMS`、`SHA256SUMS.sig` 和不含秘密的运维目录到已确认的异地目标。可以手动拷贝到离线介质；如以后采用 SSH/对象存储，应先确认目的地身份、最小写入权限、保留/删除权限及限额，不能由当前方案推定已有授权。未经授权不外发备份或通知。
7. 接收端核对签名和密文 SHA。仅校验哈希不能认证发送者：攻击者可能同时重写文件与哈希；age 的认证加密也不能证明“此密文来自指定备份操作者”，因此保留独立签名及受信验签公钥。

明文 tar 和原始备份含秘密，必须位于加密磁盘和受限目录。完成验收后按已批准保留规则清理专用临时文件；不要声称普通 `rm` 能在 SSD、快照或日志文件系统上安全擦除。不得删除唯一一份已验证备份。

### 从异地副本演练恢复

先在**独立空目录和独立空卷**执行，不覆盖开发或生产卷。操作者先核对签名公钥指纹；解密密钥通过文件或可信硬件访问，不以正文、argv 或 env 传入。

```bash
cd /RECEIVED-ENCRYPTED-COPY
ssh-keygen -Y verify -f /TRUSTED-KEYS/allowed_signers -I xiaowork-backup -n xiaowork-backup -s SHA256SUMS.sig < SHA256SUMS
sha256sum -c SHA256SUMS
umask 077
mkdir -m 700 /NEW-PRIVATE-RESTORE
age --decrypt -i /OFFLINE-KEYS/xiaowork-backup/recipient-key.txt -o /NEW-PRIVATE-RESTORE/content.tar content.tar.age
tar -tf /NEW-PRIVATE-RESTORE/content.tar
```

只接受来自已验签备份的清单。解包前确认没有绝对路径、`..` 路径、设备节点、硬链接或未允许的符号链接；不以 root 解包到根目录，不添加 tar 的 `--absolute-names`。解到新建私有目录后先运行完整维护器 `verify`，再恢复到从未使用过的 Compose project/六组空卷。拿到相应六镜像（精确 ID）、源码和 schema，不仅是一个 tar 文件。

恢复启动时 Worker/gate 默认关闭，重新登录核验管理员、revision、项目、图片 SHA、历史、current、三页 HTML/SEO、资源、旧 Session 401及备份时刻。保存各步骤起止时间、校验结果、失败原因、人工动作和达到可用状态的时间。演练结束精确停止演练项目，保留或按批准策略清理其专属资源，不清理全局 Docker。

## 密钥保管与轮换

- 解密主密钥与备份密文不能只放在同一 VPS；建议两份受控离线副本、不同物理位置，记录保管责任人和访问日志。备用密钥能否被取回也应演练。
- 公钥 recipient 可以写入受审部署配置；私钥和签名密钥只能留在受控保管位置。正式路径、责任人与取回程序尚待用户确定。
- 建议每年或人员/设备信任变化时轮换，疑似泄漏立即轮换。新备份使用新 recipient ID；验证新旧解密后再决定是否重新加密历史副本。保留旧解密密钥直至其最后一份备份到期。
- 如果密钥泄漏，只改 recipient 不能撤销已经泄漏的历史密文；按事件响应处理备份中账户 hash、session secret 和证书材料。数据库灾难恢复会撤销旧 Session，但不自动轮换所有外部凭据。

## RPO、RTO 与保留策略

以下是待用户确认的服务目标，**不是已经测得的 SLA**。当前本地恢复功能已演练，但尚无真实远端传输、下载及大数据容量耗时基线，不能声称满足正式 RTO。

| 指标/资源               | 建议目标与规则                                                     | 当前实现及缺口                                           |
| ----------------------- | ------------------------------------------------------------------ | -------------------------------------------------------- |
| 内容/数据库 RPO         | 常规最多24小时；每次源码更新、迁移、正式发布前增加完整一致备份     | 当前按命令执行；每日调度、执行时段和维护窗口未配置       |
| 异地 RPO                | 本地备份完成后24小时内复制并验签，失败即告警                       | 目的地、账号/介质、传输方式、责任人未确定                |
| 恢复 RTO                | 建议4小时内恢复为内部可验收状态，再安排入口切换                    | 需用真实容量和选定异地链路演练后确认；不保证公网切换时间 |
| 本地完整备份            | 建议7个每日 + 4个每周                                              | 含秘密、独立权限；没有自动备份删除任务                   |
| 异地密文                | 建议30个每日 + 12个每月，至少一份不可变/离线                       | 是否支持保留锁、容量和费用待决定                         |
| 当前/成功历史版本与图片 | 保留当前及所有现有成功历史引用；不因达到备份天数删除正在引用的文件 | 当前无自动GC；草稿、历史快照、预览、备份引用都要审查     |
| 失败 staging/过期预览   | 先列出任务、租约、manifest和引用，再明确审批专属目录清理           | 不实行未经验证的批量清理；磁盘满也不能删历史引用绕过门槛 |

按数据库、图片、完整静态历史、备份和构建临时区分别估算容量，并额外留出一次完整备份、一个新release和最坏构建临时空间。现有 API 的512MiB/2%临界、1GiB/10%预警仅是最小安全线，不是针对将来数据量的容量保证；无总配额、预留或跨服务磁盘配额保证。

## 容量告警、责任与值守

现有发布页面显示数据库/上传/发布目录的容量状态，warning允许继续、critical或unknown拒绝新写入/发布；后台不是推送通知服务。已有监控不会自动给邮箱、短信或企业IM发消息，不应将“管理员可能打开页面”当作可靠的离线告警送达。

上线前由用户确认：日常责任人、替补、告警接收渠道与账户、最长无人查看时间、维护窗口、可接受RPO/RTO和保留上限。建议指定 XiaoWork 站点运维负责人作为主责、用户指定另一名替补；目前角色待分配，不能虚构实际人员或邮箱。

可先采用无第三方依赖的每日人工检查：责任人打开后台容量页、核对最近备份时间和异地验签记录，并在私有运维日志签名登记。若无人能每日查看，不得将该方案标为已满足24小时RPO保障。后续自动化可用操作系统定时器每15分钟采集 `df`/本站目录用量和最近备份成功时间，只写本站私有日志；真正邮件/IM投递需另行确认账户、秘密存储和发送授权。

建议告警：任一业务卷 warning、备份/构建空间低于“下一次完整操作估算需求”、本地备份超过24小时、异地副本超过48小时、校验失败/未完成发布/恢复锁立即人工检查。critical时停止新增上传和发布，先保留现场，不执行 `docker system prune` 或删除任意历史文件。

## 本轮验收边界

- 一致性本地备份、新空卷恢复、可移植bundle验收见现有与本轮最终发行证据，不能借旧镜像结果替代新发行组。
- 当前未配置备份定时任务、外部存储、加密密钥保管、真实异地传输或自动推送告警。
- age加密、签名及异地恢复的以上流程为可执行设计，尚未在已选择的真实运维介质/账号上演练；正式运维接入前必须完成并保存证据。
- 生产部署、正式发布开关、管理员账户初始化与任何公开入口变更需要独立授权；本方案没有改变当前 gate。

依据：SQLite VACUUM INTO/WAL 官方文档、age 官方README/手册与OpenSSH `ssh-keygen` 手册。密文SHA和签名不替代应用层schema/媒体/发布完整性验证。
