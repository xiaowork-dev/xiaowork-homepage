## SQLite 根因与后继只读方案

原实现直接把原库 URI 交给 `modernc.org/sqlite v1.61.0`，使用 `mode=ro`。SQLite 的 WAL 只读支持仍有条件：已有可读 WAL/SHM、目录允许创建辅助文件，或使用 immutable。原库文件头处于 WAL 模式，停写后 WAL/SHM 均不存在，且整个源目录只读，因此 SQLite 不能创建辅助文件，底层返回 `unable to open database file (14)`。`store.checkHistory` 又把任何 SELECT 失败统一改为“schema is not initialized”，导致错误归因。后继实现先成功读取 `sqlite_schema`，只有确实没有迁移表时才报告 Schema 未初始化；其他数据库读取失败保留底层 cause。

后继维护器不再让 SQLite 打开原库，也不通过 `immutable=1`、`nolock` 或改成读写挂载来绕过限制：

1. 宿主 CLI 先取得本站独占 `operation.lock`，确认 API、Worker 和初始化写入者已停，并枚举全部运行容器。任何容器以 RW 挂载本站六个命名卷都会拒绝；不会代替操作者停止它。源卷始终 RO；apply 仅允许 publications 可写。工具不能防止另一个具有 Docker/宿主权限的管理员绕过锁，运维窗口必须确保没有此类外部写入者。
2. Linux 仅用 `O_RDONLY | O_NOFOLLOW | O_NOATIME | O_CLOEXEC` 打开原文件和数据库目录；不以读写方式打开原库，不 checkpoint、不 VACUUM 原库、不改 journal_mode。无权使用 `O_NOATIME` 时失败，不降级为可能改变访问时间的读取。数据库目录必须是实际目录，成员只能是普通的 `content.sqlite`、`-wal`、`-shm`、`-journal`；未知成员、符号链接和设备文件均拒绝。
3. 记录每个成员存在性、文件身份、完整 Linux stat 元数据和 SHA256，包括 uid/gid、mode、size、atime/mtime/ctime；目录本身也记录身份和元数据。主库、WAL、SHM、journal 总量上限为 **128 MiB**，超限拒绝。复制和再次读取均使用有界读取，检查 fstat 与路径身份一致。
4. 只把主库及 WAL 复制到新建的私有 `0700` 临时目录，副本文件 `0600`。原 SHM 作为证据读取和核对，不作为事务可信来源、不直接供 SQLite 使用。SQLite 仅以 `mode=ro` 打开副本，允许在私有目录重建辅助 SHM。维护容器 `/tmp` 为 **192 MiB tmpfs**，内存 **512 MiB**、进程数 **64**；无网络、非 root、只读根、drop ALL、no-new-privileges 不变。空间不足返回失败，临时文件不放在任何原始卷中。
5. SQLite 读取前先检查主库头、页大小及文件长度。非空 rollback journal 拒绝并要求独立人工恢复。有效 WAL 必须有正确 magic、格式、页大小、header checksum、每帧 salt 和累计 checksum，且最后一帧必须结束完整提交；截断、未提交尾、旧周期尾或其他无法证明的状态均拒绝。SQLite 本身可能合法忽略旧周期尾，维护器保守拒绝并不表示该数据库必然损坏。非空 SHM 配合不存在或空 WAL 也拒绝，不能据此假定 checkpoint 完成。
6. 在副本上执行现有 Schema/checksum、integrity、外键、业务摘要、任务终态、intent/receipt、历史引用、manifest 与全部相关文件 SHA 校验。工作区与候选核对使用同一个私有数据库视图。复制后、视图关闭时均重新核对原文件集合、元数据与 SHA；最终检查失败会传给调用方，不吞掉 `Close` 错误。
7. apply 仍只允许一个精确成员。写入修复 intent 后、unlink 前重新生成完整计划并比较；只排除本次新建的 intent 审计文件，其他状态和字节必须一致。删除候选名称后再次检查活动版本、SQLite、所有历史和文件；只有双阶段审计及最终复核成功才返回成功。

临时副本不是“运行中复制主数据库”备份。其一致性依赖**全部写入者已停止、操作锁独占、完整文件集合前后稳定**，并验证 WAL 提交边界；正式备份仍通过 SQLite 一致性机制生成备份数据库。主库/WAL/SHM 不会因 SQLite 打开副本而修改。临时目录由维护器自己生成并清理；原始数据库与故障现场不被清理。

没有 WAL 文件不等于可以忽略恢复状态。只有闭合集合稳定、没有矛盾 SHM/journal、主库与全部业务/发布证据完整时，才能继续检查。工具无法证明在运维窗口之前是否有管理员手工删除过 WAL，也不能恢复已经丢失的事务；存在此类迹象、已知非正常文件操作、校验失败或无法证明停写时必须停止，保留锁与现场，使用受审的独立恢复流程。

错误分类不再混用：`absent` 为必要文件不存在；`permission` 为读取或无修改元数据权限不足；`unsafe-file` 为未知成员/路径类型；`source-changed` 为文件身份、元数据或 SHA 变化；`wal-state-unproven` / `journal-state-unproven` 为事务文件状态不明；`schema-missing` 与 `schema-incompatible` 分别表示已检查缺表及不兼容迁移；`corrupt` 表示主文件格式或 SQLite 完整性损坏；`sqlite-open` / `sqlite-io` / `scratch-io` 保留其他打开、I/O 或私有空间错误。任何未知失败均不是自动修复许可。进入实际只读检查后出错，宿主 `operation.lock/inspection.json` 保留供人工复核。

官方依据：

- [SQLite WAL：Read-Only Databases](https://www.sqlite.org/wal.html#read_only_databases)：只读 WAL 所需条件及 WAL/SHM 行为。
- [SQLite URI filenames：immutable](https://www.sqlite.org/uri.html#uriimmutable)：immutable 跳过锁和变化检测，错误使用可能得到错误查询结果。
- [SQLite WAL file format](https://www.sqlite.org/fileformat.html#walformat)：WAL header、frame、提交与 checksum 算法。
- [SQLite locking and hot journals](https://www.sqlite.org/lockingv3.html#hot_journals)：hot journal 的恢复语义；本工具不在原库执行恢复。

真实 RO 卷结果、各失败分类、原始与后继文件 SHA256 对照、修复后备份/独立空卷恢复/更新回退及最终源码/镜像身份由本轮验收证据补记。仅代码审查或单元测试通过不能替代这些验收。

## 何时使用

发布器在创建 `current.next.<64位SHA>` 后、原子 rename 前异常退出，可能留下链接。先让原任务按正常租约和对账流程结束；公开旧版本继续服务。存在 queued/running/reconciling 任务时拒绝离线修复。不能通过直接删链接掩盖未完成的激活或恢复。

正常备份会拒绝额外符号链接。当前流程先证明它是已终结任务的冗余名称，再进行单对象修复；不跳过任何历史 manifest 或文件 SHA 校验。

## 前置条件与只读核对

1. 使用已核对完整源码身份的 maintenance 镜像 ID，保留原镜像和数据卷。
2. 只停止本站 API、Worker、api-init、publication-init 等写入者。公开静态服务可继续读取旧版本。工具不会停止其他服务，不会自动开 gate。
3. 确认没有其他运维任务。工具与 V1.1 生命周期脚本共用 `.v11-deploy/<project>/operation.lock`。
4. 执行只读计划并保存 stdout 到受限运维证据目录。计划含任务 ID、当前版本、候选目标、完整文件清单及 SHA；不含密码、数据库值或 Session。

```sh
node scripts/v11-current-repair.mjs inspect \
  xiaowork-homepage-v11-<project> \
  sha256:<maintenance-image-id> > current-repair-plan.json
```

宿主脚本在执行任何 Docker 操作前拒绝非本地 Docker endpoint，检查精确 Compose project 的写入容器已停、六个数据卷已存在。只读操作以 readonly 挂载全部源卷；修复时仅 publications 卷可写，其余卷仍 readonly。容器无网络、只读根、drop ALL、no-new-privileges，沿用非 root 维护镜像。

只读计划依次检查：

- SQLite schema、integrity、foreign keys、草稿/历史状态和未结束任务数。
- 当前相对链接、安全路径、当前版本的成功对账及每个历史 release/preview 的 manifest 与全部文件 SHA。
- 每个候选名称必须为严格 `current.next.<64hex>` 相对符号链接。
- 恰好一个受保留的激活 intent 匹配原 token 或 `SHA256(token + "/restore")`；数据库 token hash、任务分配、sealed snapshot、状态和完成时间必须一致。
- 已存在的 activation/recovery receipt 必须与 intent、完整目标 manifest 一致；恢复候选必须有完整恢复凭据。
- 成功任务必须仍指向当前目标并有激活凭据；失败任务必须已留在/恢复到前一版本。更早的历史残留若与当前版本关系不明确，保守拒绝，交由人工复核。
- 候选目标必须仍是 SQLite 保留的历史 release。计划明确标记历史引用，因此只移除临时名称，绝不删除被引用目录。
- 整个数据集合不允许未知 symlink、特殊文件或损坏历史；每个普通文件记录 bytes/SHA256。

任何一项不成立都会拒绝产生可执行计划。无效/不明对象需要保存现场和人工分析，不能改名骗过检查。

## 单对象修复

从计划读取精确候选名称和 `sha256`，填写不含秘密的人工核对原因：

```sh
node scripts/v11-current-repair.mjs apply \
  xiaowork-homepage-v11-<project> \
  sha256:<maintenance-image-id> \
  current.next.<exact-64hex> \
  <plan-sha256> \
  "已核对终态任务和完整历史，移除切换前中断的冗余名称" \
  > current-repair-result.json
```

Linux 维护器持有发布器 kernel lock，重新计算全计划 SHA。计划过期时拒绝；每次只允许指定一个对象，没有批量或强制选项。它在 unlink 前独占创建并 fsync `publications/maintenance-repairs/<id>.intent.json`，再核对链接类型/目标，仅删除该名称并 fsync 父目录。之后重新检查 SQLite、current、所有 release 和完整文件清单；除被移除的链接及本次审计文件外，所有字节 SHA 和状态必须一致，最后独占写入并 fsync `.result.json`。

返回 `verified-redundant-link-removed` 仅代表冗余链接修复已核对，**不代表新内容发布成功**。返回结果与卷内双阶段审计一并保留。数据库保持只读，不篡改任务状态或旧错误审计。

## 中断与人工处理边界

- 命令中断、磁盘不足、文件变化或复核失败时，保留现场和宿主 operation.lock；工具不启动写入服务。
- `.intent.json` 存在而 `.result.json` 缺失/损坏时，后续 inspect、备份、更新及再次修复全部拒绝。
- 此时不得删除审计/锁后盲目重试。保持本站 API/Worker 停止，先确认 current、候选是否存在、意图中的完整文件清单、历史 manifest、SQLite 终态和公开 HTTP。无法证明只有预期 unlink 时执行完整新卷灾难恢复，不覆盖原卷。
- 本版本不提供“忽略未完成审计/强制完成”的命令。需要受审人工恢复操作与新的证据，或从已验证备份重建新卷；没有自动猜测提交结果的分支。
- 修复成功后仍应重新进行实际 HTTP/SEO 核验，再运行完整备份和新卷恢复演练，确认后才能恢复本站 API/Worker。

## 修复后的完整生命周期复核

冗余链接修复与代码更新是两种操作。修复只移除经核对的临时名称，不生成新内容、不回退数据库；完整备份采用停写与 SQLite 一致性备份；恢复只写入全新空卷。代码更新必须另行调用受信生命周期工具，仍执行候选兼容性检查和新旧 maintenance 对账，不能因为备份成功就省略。

本轮专用控制器 `scripts/p6e-final-current-repair-test.mjs` 的顺序为：真实 Nuxt 切换前中断 → 终态任务/intent/历史/全部文件 SHA 只读计划 → 证实修复前备份拒绝 → 单对象修复与逐文件 SHA 对比 → 完整备份 → 全新空卷恢复 → 使用统一六角色发行组启动 → 验证旧 Session 拒绝、原密码重新登录、草稿/私有图片/任务历史/公开 HTML 与 SEO → 真正执行 `v11-release.mjs update` → 复核停写备份、新旧离线对账、HTTP、管理后台、图片和操作锁 → 仅停止这两个新测试项目，保留卷和镜像。

修复专项中的 update 使用同源码最终六角色组，验证修复后的数据可以再次进入正常生命周期；不同源码版本的升级与回退由 [跨源码验收报告](P6E-CROSS-SOURCE-ACCEPTANCE.md) 单独验证。本流程保持发布 gate 关闭、Worker 默认不启动，不能代表生产上线授权。完整计划和回执保留在私有本地控制器缓存及持久卷内双阶段审计；公开证据记录聚合 SHA、文件数和逐文件一致性结论，不上传数据库、备份或凭据。
