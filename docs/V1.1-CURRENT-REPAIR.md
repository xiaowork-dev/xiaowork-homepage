# V1.1 `current.next.*` 离线核对与单对象修复

适用范围：P6-E 最终闭环。命令是受信运维工具，不是 HTTP API，也不是发布任务参数。它只移除已经证明冗余的单个临时链接，保留 `current`、全部 release、快照、图片、任务和数据库。正式服务器操作仍需用户另行授权。

**2026-10-28 最终验收状态：阻塞。** 冻结源码 `817aa533741bdd5de23f322fa5e5171442cb28a9` 的严格只读卷实测暴露 SQLite WAL 读取问题，尚未执行实际链接修复。以下命令和保护规则描述现有实现契约，不能作为该发行组已经通过真实卷修复验收的声明。不得在正式环境尝试绕过只读/完整性检查；需要后继源码修复、统一重建六角色及重新验收。

## 何时使用

发布器在创建 `current.next.<64位SHA>` 后、原子 rename 前异常退出，可能留下链接。先让原任务按正常租约和对账流程结束；公开旧版本继续服务。存在 queued/running/reconciling 任务时拒绝离线修复。不能通过直接删链接掩盖未完成的激活或恢复。

正常备份会拒绝额外符号链接。当前流程先证明它是已终结任务的冗余名称，再进行单对象修复；不跳过任何历史 manifest 或文件 SHA 校验。

## 前置条件与只读核对

1. 使用已核对完整源码身份的 maintenance 镜像 ID，保留原镜像和数据卷。
2. 只停止本站 API、Worker、api-init、publication-init 等写入者。公开静态服务可继续读取旧版本。工具不会停止其他服务，不会自动开 gate。
3. 确认没有其他运维任务。工具与 V1.1 生命周期脚本共用 `.v11-deploy/<project>/operation.lock`。
4. 执行只读计划并保存 stdout 到受限运维证据目录。计划含任务 ID、当前版本、候选目标、完整文件清单及 SHA；不含密码、数据库值或 Session。

```sh
node scripts/v11-current-repair.mjs inspect \
  xiaowork-homepage-v11-<project> \
  sha256:<maintenance-image-id> > current-repair-plan.json
```

宿主脚本在执行任何 Docker 操作前拒绝非本地 Docker endpoint，检查精确 Compose project 的写入容器已停、六个数据卷已存在。只读操作以 readonly 挂载全部源卷；修复时仅 publications 卷可写，其余卷仍 readonly。容器无网络、只读根、drop ALL、no-new-privileges，沿用非 root 维护镜像。

只读计划依次检查：

- SQLite schema、integrity、foreign keys、草稿/历史状态和未结束任务数。
- 当前相对链接、安全路径、当前版本的成功对账及每个历史 release/preview 的 manifest 与全部文件 SHA。
- 每个候选名称必须为严格 `current.next.<64hex>` 相对符号链接。
- 恰好一个受保留的激活 intent 匹配原 token 或 `SHA256(token + "/restore")`；数据库 token hash、任务分配、sealed snapshot、状态和完成时间必须一致。
- 已存在的 activation/recovery receipt 必须与 intent、完整目标 manifest 一致；恢复候选必须有完整恢复凭据。
- 成功任务必须仍指向当前目标并有激活凭据；失败任务必须已留在/恢复到前一版本。更早的历史残留若与当前版本关系不明确，保守拒绝，交由人工复核。
- 候选目标必须仍是 SQLite 保留的历史 release。计划明确标记历史引用，因此只移除临时名称，绝不删除被引用目录。
- 整个数据集合不允许未知 symlink、特殊文件或损坏历史；每个普通文件记录 bytes/SHA256。

任何一项不成立都会拒绝产生可执行计划。无效/不明对象需要保存现场和人工分析，不能改名骗过检查。

## 单对象修复

从计划读取精确候选名称和 `sha256`，填写不含秘密的人工核对原因：

```sh
node scripts/v11-current-repair.mjs apply \
  xiaowork-homepage-v11-<project> \
  sha256:<maintenance-image-id> \
  current.next.<exact-64hex> \
  <plan-sha256> \
  "已核对终态任务和完整历史，移除切换前中断的冗余名称" \
  > current-repair-result.json
```

Linux 维护器持有发布器 kernel lock，重新计算全计划 SHA。计划过期时拒绝；每次只允许指定一个对象，没有批量或强制选项。它在 unlink 前独占创建并 fsync `publications/maintenance-repairs/<id>.intent.json`，再核对链接类型/目标，仅删除该名称并 fsync 父目录。之后重新检查 SQLite、current、所有 release 和完整文件清单；除被移除的链接及本次审计文件外，所有字节 SHA 和状态必须一致，最后独占写入并 fsync `.result.json`。

返回 `verified-redundant-link-removed` 仅代表冗余链接修复已核对，**不代表新内容发布成功**。返回结果与卷内双阶段审计一并保留。数据库保持只读，不篡改任务状态或旧错误审计。

## 中断与人工处理边界

- 命令中断、磁盘不足、文件变化或复核失败时，保留现场和宿主 operation.lock；工具不启动写入服务。
- `.intent.json` 存在而 `.result.json` 缺失/损坏时，后续 inspect、备份、更新及再次修复全部拒绝。
- 此时不得删除审计/锁后盲目重试。保持本站 API/Worker 停止，先确认 current、候选是否存在、意图中的完整文件清单、历史 manifest、SQLite 终态和公开 HTTP。无法证明只有预期 unlink 时执行完整新卷灾难恢复，不覆盖原卷。
- 本版本不提供“忽略未完成审计/强制完成”的命令。需要受审人工恢复操作与新的证据，或从已验证备份重建新卷；没有自动猜测提交结果的分支。
- 修复成功后仍应重新进行实际 HTTP/SEO 核验，再运行完整备份和新卷恢复演练，确认后才能恢复本站 API/Worker。

## 修复后的完整生命周期复核

冗余链接修复与代码更新是两种操作。修复只移除经核对的临时名称，不生成新内容、不回退数据库；完整备份采用停写与 SQLite 一致性备份；恢复只写入全新空卷。代码更新必须另行调用受信生命周期工具，仍执行候选兼容性检查和新旧 maintenance 对账，不能因为备份成功就省略。

本轮专用控制器 `scripts/p6e-final-current-repair-test.mjs` 的顺序为：真实 Nuxt 切换前中断 → 终态任务/intent/历史/全部文件 SHA 只读计划 → 证实修复前备份拒绝 → 单对象修复与逐文件 SHA 对比 → 完整备份 → 全新空卷恢复 → 使用统一六角色发行组启动 → 验证旧 Session 拒绝、原密码重新登录、草稿/私有图片/任务历史/公开 HTML 与 SEO → 真正执行 `v11-release.mjs update` → 复核停写备份、新旧离线对账、HTTP、管理后台、图片和操作锁 → 仅停止这两个新测试项目，保留卷和镜像。

修复专项中的 update 使用同源码最终六角色组，验证修复后的数据可以再次进入正常生命周期；不同源码版本的升级与回退由 [跨源码验收报告](P6E-CROSS-SOURCE-ACCEPTANCE.md) 单独验证。本流程保持发布 gate 关闭、Worker 默认不启动，不能代表生产上线授权。完整计划和回执保留在私有本地控制器缓存及持久卷内双阶段审计；公开证据记录聚合 SHA、文件数和逐文件一致性结论，不上传数据库、备份或凭据。
