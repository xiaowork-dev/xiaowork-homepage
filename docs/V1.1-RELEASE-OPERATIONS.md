# V1.1 部署、更新和代码回退

本说明对应新增 `scripts/v11-*` 工具。旧 `release.sh/deploy.sh/update.sh/rollback.sh` 只服务 V1.0 镜像，不能覆盖 V1.1 多服务、SQLite和发布状态。两套工具不共用 `.env`、`.deploy`、容器、端口和数据卷。P6-E只在本地模拟，不访问生产。

## 经过验收的版本描述符

版本描述符包含完整40位Git SHA、明确schema版本和六个实际 `sha256:` 镜像 ID（api、worker、gateway、frontend、static、maintenance）。工具拒绝浮动镜像tag作为运行身份，并要求Worker OCI源码标签与完整SHA一致；本地Git必须确实存在该提交。

```bash
node scripts/v11-release.mjs attest \
  --source <完整已验收GitSHA> --schema 3 \
  --api <已验收API镜像> --worker <已验收Worker镜像> \
  --gateway <已验收后台网关镜像> --frontend <保留V1.0兼容资源的静态镜像> \
  --static <已验收静态服务镜像> --maintenance <已验收维护镜像> \
  --out .cache/reviewed-v11-release.json
```

这是固定镜像身份工具，不是签名发布系统或自动验收。操作者必须先检查对应源码、依赖、镜像扫描和测试结果；不能给未验收镜像随意填写一个SHA。工具为已核验镜像建立本站专属 retained tag，保留旧代码镜像；不会删除 V1.0 或其他项目镜像。

从GitHub获取版本时使用另一个独立目录、`git fetch` 和完整SHA检出，不在V1.0目录执行覆盖式pull。代码仓库、构建代理、私有仓库凭据均不挂载到API/Worker。当前工具不创建或保管GitHubToken，也不让网页执行git或shell。构建和分发镜像由受控离线发布操作完成。

## 初次部署

前置条件：本地Docker Engine与Compose（支持`!override`）、Node.js22+、可用已验收镜像、已验收schema及空闲回环端口/网段。工具明确拒绝SSH/TCP Docker context；正式服务器执行须在将来获授权后由操作者登录该机，P6-E不连接。

运行任何Docker命令前先检查 `DOCKER_HOST`，只允许明确的本机Unix socket或Docker Desktop Linux命名管道；显式 `DOCKER_CONTEXT` 也按该名称检查endpoint，防止环境变量将操作转向远程daemon。纯本机测试设置 `tcp://invalid.example:2375` 后实际验证在任何Docker调用前拒绝，没有连接该地址。

```bash
bash scripts/v11-deploy.sh \
  --project xiaowork-homepage-v11-isolated \
  --manifest .cache/reviewed-v11-release.json \
  --topology simulation --http-port 3216 --https-port 3449 \
  --subnet 192.168.245.0/28
```

默认Worker profile和发布gate均关闭。`simulation`使用可信本地HTTPS和专属CA；初次管理员仍需真实TTY安全初始化，无默认密码。只有本地独立验收才能显式`--local-publish 1`。`openresty`拓扑固定正式origin、只有回环HTTP入口、不允许开启本地发布gate，生产发布安全门槛不会被部署工具绕过。

本站状态写入忽略目录 `.v11-deploy/<项目>/`，目录700/文件600；其中无密码或token。包含当前/前一份完整描述符、生成Compose覆盖、首次初始化记录和可能的人工恢复记录。原V1.0 `.deploy`不变。初次部署中断仅能用同一描述符/同一拓扑恢复，不能把未知同名容器/旧卷当作可覆盖的空环境。所有volume均保留。

```bash
node scripts/v11-release.mjs status --project xiaowork-homepage-v11-isolated
node scripts/v11-release.mjs stop --project xiaowork-homepage-v11-isolated
```

`stop`只对显式本站项目执行不带`-v`的Compose down，保留数据库、图片、发布、会话和证书卷及镜像。禁止用全局prune代替。

## 更新与失败恢复

```bash
bash scripts/v11-update.sh \
  --project xiaowork-homepage-v11-isolated \
  --manifest .cache/next-reviewed-v11-release.json
```

实际顺序：取得本站独占生命周期锁 → 校验候选完整SHA/镜像/schema → 停止本项目写入 → 确认无未完成任务及旧库完整 → 一致备份全部数据 → 原卷启动候选服务 → 等健康检查 → 仅请求本机回环的首页、项目、关于、health和后台入口 → 成功后原子记录当前/前一版本。

候选启动前，工具先保留已有 `operation.lock`，再原子写入 `recovery-required.json` 转换意图。只有候选健康、HTTP、当前/前版记录全部完成，或旧服务、数据库、原描述符和HTTP已验证恢复后，才解除阻断。即使首次意图写入因磁盘满失败，锁也保留；Linux文件与父目录执行fsync，Windows支持文件fsync但Node不提供目录fsync，不能把本机进程故障测试扩大为断电持久性保证。

候选失败时不会直接恢复旧数据库覆盖新写入。先停候选写服务，再用原版本维护工具核验schema、内容及发布状态；兼容才启动原服务，并重新验证HTTP与原当前版本记录。**停止候选本身失败**也属于人工恢复状态，不能假定写服务已经停止。原服务无法安全核验时保留 `operation.lock`、初始转换意图、备份与候选/原描述符，尝试更新 `recovery-required.json`；恢复记录更新失败仍不释放锁。禁止删记录或锁盲目重跑，必须由操作者完成DB/current/manifest/HTTP核对并记录决定。

本版只自动处理**schema相同且旧检查器接受的更新/回退**。schema变化一律先拒绝，要求另写经过验收的备份、迁移、兼容窗口和回退方案。不会自动降级、删库或恢复旧schema掩盖问题。一次性初始化与显式已有数据库版本检查均采用既有非破坏性迁移代码。

P6-E 的本地生命周期验收范围是同一完整源码 SHA、同 schema3 的镜像重新封装和实际容器替换，以及测试专用损坏候选；它不证明不同功能源码版本的升级兼容，也不证明跨 schema 迁移。当前与历史发布格式仍有同源码/同构建身份的保守恢复限制，正式升级前必须另测真实源版本组合。

2026-10-28 实测五项通过，见 [生命周期证据](evidence/P6E-release-lifecycle.json)：真实同源码/同schema gateway镜像替换、回退旧镜像、移除nginx可执行文件的候选启动失败后自动恢复旧服务并HTTP复验、schema4候选在替换写服务前拒绝、已有独占锁时拒绝且不移除他人锁。公开首页/项目/关于/release marker 的字节SHA在操作前后相同。首轮仅修改镜像ENTRYPOINT的fixture被Compose固定entrypoint覆盖，没有产生故障，测试未通过；保留[首轮测试证据](evidence/P6E-release-lifecycle-first-fixture.json)，随后改用真实缺失固定可执行文件的独立候选复测通过。未修改生产容器和原数据卷。

新增宿主CLI边界测试已实际验证：真实损坏候选启动失败后，测试专用wrapper让第二次本站writer-stop命令失败，并让恢复记录更新返回ENOSPC；初始转换意图与operation.lock保留，重复update拒绝。经明确测试操作者停写、旧维护器核验、恢复固定旧镜像和HTTP/内容SHA后才释放阻断，见 [恢复阻断证据](evidence/P6E-release-guard.json)。这是宿主命令和文件写入边界注入，不代表实际Docker daemon整体故障或物理磁盘耗尽。首轮人工恢复后的HTTP连接复用发生reset，锁继续保留；[首轮连接失败证据](evidence/P6E-release-guard-first-connection-attempt.json)保留，独立连接复验后重新完成测试。故障fixture只由测试CLI `--import` 装载，不进入API/Worker或公网请求路径。

更新会产生管理/发布短暂停机，候选替换网关或静态容器可能产生短暂HTTP失败；不能宣称零停机。正式切换应在维护窗口执行，保留V1.0独立容器与回环入口，反代回退仅更换本站上游。

## 代码回退与内容恢复

```bash
bash scripts/v11-rollback.sh --project xiaowork-homepage-v11-isolated
```

此命令使用本站 `previous.json` 内的完整代码/镜像身份，先备份，再走相同兼容性、健康、HTTP及失败恢复路径。不会把SQLite回到旧时间点。缺少前版本、镜像已丢失或schema不兼容均拒绝。

后台“恢复内容版本”只切换已成功且完整兼容的静态release，不更改代码镜像、schema或草稿。P6-D的保守限制仍为同源码、同Worker构建身份及内容格式。数据库灾难恢复另见[备份恢复](V1.1-BACKUP-RESTORE.md)，只允许独立空卷，且会丢失备份之后的编辑。

## 运行边界

没有生产SSH/Cloudflare/1Panel自动化；没有DockerSocket挂入服务、任意shell API或不受控构建下载。公开前还需通过P6-E强制故障、安全和备份验收，以及用户最终授权。自动HTTP探测只证明固定路径返回成功，完整数据、SEO、图片和认证需结合专属集成/浏览器验收。
