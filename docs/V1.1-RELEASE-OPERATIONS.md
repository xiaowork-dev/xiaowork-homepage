# V1.1 部署、更新和代码回退

## 生产拓扑的真实客户端地址（2026-11-08）

**问题**：`openresty` 拓扑中，宿主 OpenResty 经回环端口和 docker-proxy 连到 gateway，gateway 看到的 `$remote_addr` 对所有访客都相同。原配置 `X-Forwarded-For $remote_addr` 把这个地址交给 API，导致登录挑战（每来源 10 个未消费）和密码尝试（每"来源 + 用户名"每 15 分钟 5 次）变成全局共享。匿名用户可以借此持续锁死管理员登录，审计中的来源桶也失去意义。

**修复**（只影响 `openresty` 拓扑，`simulation` 不变）：

- 生命周期工具把 edge 网络固定为控制网段同一 /24 中的 `.16/28`（例如 `192.168.248.0/28` 对应 `192.168.248.16/28`），并为每个项目生成 `gateway-realip.generated.conf`（0644，不含机密），只读挂载到 gateway。
- gateway 只信任来自这个 edge /28 的 `X-Real-IP`（`set_real_ip_from`、`real_ip_header X-Real-IP`、`real_ip_recursive off`），然后照旧用 `X-Forwarded-For $remote_addr` 把恢复出的真实地址交给 API。API 仍然只信任 gateway 的 `.2/32`。
- 内部 control/isolated 网络上的容器不在信任范围内，伪造的 `X-Real-IP` 会被忽略。没有 `X-Real-IP` 的宿主本机请求会共用 edge 网桥地址这一个桶。生成的配置文件缺失时，gateway 启动失败（fail-closed）。

**上线前提**：

- 本站 OpenResty 反代必须设置 `proxy_set_header X-Real-IP $remote_addr;`。1Panel 默认的 `proxy/root.conf` 已包含这一行，切换上游时必须保留。
- 如果以后给根域名开启 Cloudflare 代理（橙云），必须先在 OpenResty 层按 Cloudflare 官方网段配置 real_ip，否则真实地址会退化成 Cloudflare 边缘 IP。
- 部署前要确认 `192.168.N.0/28` 和 `192.168.N.16/28` 都未被占用；冲突时 Docker 会拒绝创建网络，部署失败、不会启动。

## 最新：共同维护屏障（2026-11-01）

本轮新增 API、Worker、离线运维共同遵守的 Linux 文件锁协议，详见[专项验收](P6E-MAINTENANCE-TESTS.md)。它改变正式运行源码；下方 chain4/4f18 是历史基线，不能作为此实现的运行发行身份。本轮没有准备原生 Linux Engine，没有重跑完整备份链，也没有构建可上线的最终六角色。

### 控制卷和权限

每个项目独占 `<project>_admin-maintenance-control`，与六个业务数据卷分离。Compose 向 API 和 Worker **只读**挂载 `/control`；受信维护镜像中的 `/homepage-control` 才获得该卷的读写挂载。目录 UID/GID 10001、0700；锁文件 0400，状态/审计 0600。运行服务没有初始化、解锁或修改状态的 HTTP 接口，Worker 无数据库、Docker Socket、SSH/GitHub 凭据，网络仍为 none。

控制目录包含固定 inode 的 `admission.lock`、`activity.lock`，以及严格校验的 `state.json`。状态只接受格式 1、`ready/idle` 或 `recovery-required/draining|drained` 与操作 owner；未知字段、尾随 JSON、超限、非普通文件、硬链接、符号链接、缺失/不可访问的目录及未完成的 `state.next` 均失败关闭。逐段 `openat(O_NOFOLLOW)`，不以路径字符串转换代替身份校验。

`init` 仅能显式初始化**空**控制卷；不存在自动启动时重设 ready 的逻辑。已有卷、未知锁或失败操作不能再次 init。新部署由 `provisionControl` 创建精确名称及 Compose 标签的新卷，再初始化；独立开发 Compose 的 `control-init` 是需要显式调用的 maintenance profile，不随正常 up 启动。手工运行它之前必须构建并指定本次已核验、包含 `/homepage-control` 的维护镜像；不能采用旧 maintenance 标签冒充新实现。

### 原子边界与排空

1. API 在授权和数据库查询之前取得 admission 独占锁，检查 ready，再取得 activity 共享锁；立即释放 admission，持共享租约直到响应及 SQLite Commit 完成。登录 challenge 也会写数据库，因此整个管理 API 都受保护。`/healthz`、`/readyz` 继续可用。
2. Worker 的 `RunNext` 在 Claim 前取得同一共享租约，覆盖构建、准备、原子激活、HTTP 核对及最终结果回写。API 的私有 Claim 也执行普通 admission；维护与领取交错时 Claim 返回特定 503，Worker 空闲等待，不把它当成新的失败任务。
3. 运维先取得宿主 `operation.lock`，再通过 admission 独占锁将 `recovery-required/draining` fsync 落盘，之后释放 admission，等待 activity 独占锁。此刻新管理请求和新 Claim 已原子拒绝；进程死亡不会重新开放它们。
4. 已领取的任务采用**等待完成**策略，允许它完成激活与最终对账；其共享租约持续阻止维护进入数据检查。私有 heartbeat/prepared/result 只在 ready 或 draining 取得短共享租约，drained 后拒绝。运维绝不能在仅看到 draining 时开始读取/修复源卷。
5. activity 独占锁取得后，在 admission 锁下记录并 fsync `drained`。随后可以退出控制子进程：持久状态继续拒绝新租约，排空不依赖父监督进程存活。运维仍需安全停止并验证所有本站写入者及挂载范围，才能进行严格只读核对。
6. 全部外层检查成功并写审计后，持有同进程操作能力的宿主才调用 `complete`；它重新校验 owner、drained 和独占 activity，写完成回执、fsync，再原子写回 ready。失败、异常退出、超时、控制状态未知均不自动 complete，不在 finally 删除未知锁。

新任务创建的 SQLite 事务在共享租约内部提交；共享文件锁没有伪装成跨 SQLite/文件系统的分布式事务，而是保证维护的排空边界在这些事务结束之后。已提交但尚未领取的 queued 任务会被保留，离线备份继续按原契约拒绝 unfinished 任务；不丢弃任务，也不为方便维护强行激活它。

### 锁顺序和故障处理

API：admission → activity SH → 释放 admission → SQLite 事务 → 释放 SH。Worker：既有 publisher 生命周期锁 → admission → activity SH → 释放 admission → UDS/构建/激活/结果 → 释放 SH。维护：宿主操作锁 → admission 写封门状态 → 释放 admission → 等待 activity EX → admission 写 drained → 释放文件锁 → 停止 Worker/API/init → 原有 publisher/只读维护锁。等待 activity 时不持 admission；完成状态检查时只尝试非阻塞 activity EX，避免反向等待导致死锁。正常 admission 竞争只等待一秒，超时失败关闭。

维护排空最长 12 分钟；超时、构建未能对账、租约丢失等均保留 recovery-required。不得按 PID 消失、过期时间或重启自动认领、清锁。`draining` 的未知中断不能用 `complete` 处理；必须独立人工核对在途任务、current、intent/receipt、manifest、全部文件 SHA、挂载和写者，另行形成恢复决定。本轮未提供“任意解锁”工具。已确认 drained 的操作也必须通过完整外层检查才可由原受信上下文正常完成。

共享屏障是协作式互斥，不能防御掌握 Docker/root 的操作者故意绕开协议。它不替代 SQLite/schema/current 完整性检查，不使活跃 RW 容器自动变成只读；严格只读验收仍须停止所有写者。源卷 Source、nocopy、O_NOATIME、私有 SQLite 副本及全部元数据断言均保持。

真实进程/HTTPS/固定离线 Nuxt 专项、内核 RO 控制卷、宿主强杀与外层断言已通过，原始失败保留。测试镜像含 `_test.go` 检查点，明确标为测试，不可写进正式发行描述符。API/Worker 的正式 Dockerfile 不编译这些入口。

## 活跃发布与维护协作的未完成门槛

宿主锁只约束受信`v11-*`工具，未挂给API/Worker；`createPublicationJob`、UDS `workerClaim`、Worker `RunNext`不读宿主marker。Worker的publisher内核锁是另一把锁。监督进程检测子控制器退出后才停写，有窗口；父监督退出时也不能依赖补救。不能承诺维护锁建立后活跃发布均拒绝，或服务带marker重启会禁写。

后继最小扩展应复用现有UDS/锁/对账，加入独立持久且API/Worker/维护器共同可见的控制目录，不增加Worker的DB/秘密/DockerSocket挂载。以下是**待实现/验收条件，不是已提供命令**：

- 受信入口原子建立/fsync维护请求及epoch；API的新publish/preview/rollback和影响备份的写操作在同一屏障下核验，避免“读marker后再开始事务”的TOCTOU。新任务返回明确维护错误，不得202后执行。
- Worker领取与激活遵守屏障；在途原任务在允许的lease内完成终态对账，或保留恢复状态，不能强杀后猜current。任务/全部写者未确认静止时禁止离线读取/修复/备份。
- 控制器SIGKILL、父监督退出、容器异常和重启不解除屏障；API/Worker启动先核验。缺失、损坏、未知owner/epoch失败关闭，PID消失/租约超时不是解锁许可。
- 运行互斥与recovery-required分离；只有受信入口完成SQLite/FS/intent/receipt/HTTP及整链断言后才能解除自己的正常状态，未知失败不得自动清理。
- 真实测试同时到达、控制器SIGKILL、父监督退出、锁建立API未停、Worker在途、marker下重启六场景，记录认证HTTP、任务/DB、current、锁/marker前后状态，并复验正常功能。运行变更重新冻结六角色及完整链。

本轮没有实现共享屏障，六动态场景全部NOT_RUN；宿主工具拒绝和停API后的502不替代。此项是独立生产工程阻塞，不能降低TLS/CSRF/Cookie或忽略marker绕过。

## 初次部署

前置条件：本地Docker Engine与Compose（支持`!override`）、Node.js22+、可用已验收镜像、已验收schema及空闲回环端口/网段。工具明确拒绝SSH/TCP Docker context；正式服务器执行须在将来获授权后由操作者登录该机，P6-E不连接。

运行任何Docker命令前先检查 `DOCKER_HOST`，只允许明确的本机Unix socket或Docker Desktop Linux命名管道；显式 `DOCKER_CONTEXT` 也按该名称检查endpoint，防止环境变量将操作转向远程daemon。纯本机测试设置 `tcp://invalid.example:2375` 后实际验证在任何Docker调用前拒绝，没有连接该地址。

```bash
bash scripts/v11-deploy.sh \
  --project xiaowork-homepage-v11-isolated \
  --manifest .cache/reviewed-v11-release.json \
  --topology simulation --http-port 3216 --https-port 3449 \
  --subnet 192.168.245.0/28
```

默认Worker profile和发布gate均关闭。`simulation`使用可信本地HTTPS和专属CA；初次管理员仍需真实TTY安全初始化，无默认密码。只有本地独立验收才能显式`--local-publish 1`。`openresty`拓扑固定正式origin、只有回环HTTP入口、不允许开启本地发布gate，生产发布安全门槛不会被部署工具绕过。当前实现尚无可启用正式origin发布的生产gate；需要另行设计、实现、验收并取得上线授权，不能将本地测试开关或localhost配置复制到生产。

本站状态写入忽略目录 `.v11-deploy/<项目>/`，目录700/文件600；其中无密码或token。包含当前/前一份完整描述符、生成Compose覆盖、首次初始化记录和可能的人工恢复记录。原V1.0 `.deploy`不变。初次部署中断仅能用同一描述符/同一拓扑恢复，不能把未知同名容器/旧卷当作可覆盖的空环境。所有volume均保留。

```bash
node scripts/v11-release.mjs status --project xiaowork-homepage-v11-isolated
node scripts/v11-release.mjs stop --project xiaowork-homepage-v11-isolated
```

`stop`只对显式本站项目执行不带`-v`的Compose down，保留数据库、图片、发布、会话和证书卷及镜像。禁止用全局prune代替。

实际顺序：取得本站独占生命周期锁 → 校验候选完整SHA/六角色镜像/schema → 停止本项目写入 → 旧、新维护器核验现有SQLite、图片、快照及历史manifest，确认无未完成任务 → 一致备份全部数据 → 原卷启动候选服务并等健康检查 → 再次停写，比较新旧检查器状态及17张固定业务/schema/发布历史表的逻辑内容摘要 → 恢复候选服务并核验本机HTTP → 成功后原子记录当前/前一版本。

HTTP核验包括首页、项目、关于、health、robots、sitemap、后台shell及其真实JS/CSS；模拟拓扑通过显式本地CA验证可信HTTPS的Session401、challenge200和Secure/HttpOnly/SameSite Cookie。已发布内容还按当前manifest逐文件比较HTTP字节大小和SHA256，并核对release marker。状态码200或容器healthy本身不代表更新成功。Session、challenge、限速、审计和幂等控制表不进入逻辑内容摘要，但一致性备份仍校验全部物理文件。

候选启动前，工具先保留已有 `operation.lock`，再原子写入 `recovery-required.json` 转换意图。只有候选健康、HTTP、当前/前版记录全部完成，或旧服务、数据库、原描述符和HTTP已验证恢复后，才解除阻断。即使首次意图写入因磁盘满失败，锁也保留；Linux文件与父目录执行fsync，Windows支持文件fsync但Node不提供目录fsync，不能把本机进程故障测试扩大为断电持久性保证。

候选失败时不会直接恢复旧数据库覆盖新写入。先停候选写服务，再用原版本维护工具核验schema、内容及发布状态；兼容才启动原服务，并重新验证HTTP与原当前版本记录。**停止候选本身失败**也属于人工恢复状态，不能假定写服务已经停止。原服务无法安全核验时保留 `operation.lock`、初始转换意图、备份与候选/原描述符，尝试更新 `recovery-required.json`；恢复记录更新失败仍不释放锁。禁止删记录或锁盲目重跑，必须由操作者完成DB/current/manifest/HTTP核对并记录决定。

本版经过验收的范围是**schema3且新旧检查器均接受现有完整数据的更新/回退**，不代表任意两个相同schema标号的源码天然兼容。schema变化一律先拒绝，要求另写经过验收的备份、迁移、兼容窗口和回退方案。当前没有跨schema自动迁移或降级；不会删库或恢复旧schema掩盖问题。一次性初始化与显式已有数据库版本检查均采用既有非破坏性迁移代码。
